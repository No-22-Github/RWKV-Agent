## 判据设计要点
- 每轮 `required_tools:["bash"]`，`output_contains` 全部用多位数/时间戳/请求 id（如 `r-3fa91c`、`14:00:00`、计数），`output_contains_token:true` 防嵌入误中。计数题同时要求"最早/最后一条的时间"，top-N 要求名称 + 次数，最慢要求 req_id + 耗时，异常题要求 req_id + 时间。没有 output_excludes（正确回答可能提到"直接 grep 会得到 N"，排除会误伤）；子串陷阱的错误值写在 `trap_decoys`。
- 陷阱是造数据时有意放的：目标状态码同时出现在别的行的 dur/bytes/路径里（`/api/cart/404`）；窗口边缘（下沿、上沿、上沿前 1 ms/1 s）各放了事件；top-N 保证前 N+1 名次数互不相同；最慢 N 保证第 N 与 N+1 不并列。
- nginx 的 rt 单位是秒，最慢题只判请求编号（不要求 ms 数值）。
- verify.py：先校验 fixture sha256，用独立的逐行解析器（正则/json）重算每一轮的全部期望 token，并断言与 case.json 一致；不依赖 bash。

## 已知风险
- 时间 token：题面（含此前轮次）要求“几点几分几秒”的保持 HH:MM:SS，其余改为 HH:MM（"14:03" 与 "14:03:27" 都能过）。
- top-N 题的次数 token 是普通整数，老师若只列名称不列次数会判错（题面均要求"各多少"）。
- 窗口题边缘事件靠 awk 字符串比较，老师若用 grep 小时前缀近似会漏掉分钟级边界。
- 日志是合成的，服务/路径名在不同题间来自 4 套词表，重复度中等。
