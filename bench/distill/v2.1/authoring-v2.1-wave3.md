## 2. 上一轮老师跑完后发现的问题（必须避免）

1. **行为题要让"正确做法"有充分理由**。b21c（查不到就说没有）老师只过了 30/78，b21d（先确认/先追问）52/117：老师没发现两处配置冲突、该确认就直接删了、指代不清时把两个都答了。这些失败判分没错，但题目要让情境足够明确——冲突要放在正常路径一定会读到的两个文件里；"要确认"的操作要明显不可逆（删整目录、覆盖唯一一份内容）；"要追问"的请求要确实无法从工作区判断用户指哪个。
2. **判据别卡写法**：英文关键词大小写都收（`Alpha`/`alpha`），中文同义说法收全；`output_excludes` 不要放诚实回答也会用到的词。
3. **终答长度**：训练过滤会丢掉超过 600 字的终答。只有 `rewrite_text`、`draft_document`、`code_help`、`summarize_page` 这四类 task_type 放宽到 2000 字；其他题的答案要能在 600 字内说清（写进文件的长内容不算终答）。
4. **上下文长度**：训练按 16k token 切，单行超长会被丢。整篇读取的文件控制在 3000 token 以内；计算题的数据 150–250 行、每行要短，题目设计成用 bash 处理而不是把整个文件读进来。
5. **工具目录**：每题 `must_offer` 必须包含一条完整通过路径所需的全部工具（没写 must_offer 的题会随机抽到缺工具的紧凑目录）。
6. 1–3 位的裸数字判据要开 `output_contains_token` 或带上下文；只问"几点"的不要判到秒。
7. **App 暂存**：老师和学生都在 App harness 下跑，所有写文件都先暂存、需要用户确认。答案说"已暂存待确认"是对的，判据不要要求"已保存"，也不要禁止"暂存"。多轮题里如果需要模拟用户确认或拒绝改动，用 `Turn.review_before`（`accept` / `reject`）。
8. 每题一个独立题族，fixture 内容、文件名、数值都不同，不要换数字套模板；网页题的 URL、站点名也要各不相同。
