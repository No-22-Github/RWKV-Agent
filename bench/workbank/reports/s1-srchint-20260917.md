# S1 信息源定位句实验（srchint 轴）

日期：2026-09-17 · 分支 `workbank/closeout`（代码与报告均未提交）
动因：人工核实确立 workbank 37 失败题主因 = G1K 按工具名字面联想、不按信息来源选工具（II-a 10 题、web 题 4/4 弃答）。
设计：S0 = `closeout-v0-g1k`；S1 = 同 wire + System 第二行加一句信息源定位（`+src-hint` 修饰项，产品默认 off、控制字节不变）。

句子（workbank 目录下 40 题逐字节一致；目录自适应——bfcl 无 web 工具时自动只剩本地半句）：

> The user's files are in the current workspace; use list_files, search_text and read_file for them. Use web_search and web_fetch only for public information that is not in the workspace.

## 判定（按预定规则）：S1 无改善 → 走第二分支

问题不在「System 没给信息源的定位」，而是模型对工具目录的语义理解本身弱（按名字联想）。下一轮应转向工具命名对齐训练分布、state 或语料。且本句有明确负副作用，不建议并入产品 wire。

## 副作用一：step-1 结构断裂 4 → 12

- 7 例 think 跑飞（如 fs-0001：2126 字符 think 在「list_files 还是逐个读文件」之间摇摆到 EOS，无调用无闭合）；
- 5 例信封不闭合（如 tab-0003：推理全对、`ILD{"name":"list_files",...}` 发出后无闭合标记即 EOS）；
- 机制读法：句子给了模型更多可推理素材，贪心解码被推入更长、不收敛的 think——「step-1 闭合纪律」这个新桶被直接放大。

## 副作用二：bfcl no-call 漂移（护栏未通过）

irrelevance 20 题：**4 例 S0 零调用 → S1 调了工具**（irr_9/irr_10 首步 `list_files`、irr_22 首步 `search_text`、irr_11 全程）——恰是句子里点名的工具，因果直接。irrelevance 通过 12 → 10；全库 49/60 → 47/60（另 state_multi_turn_base_3、recovery_multi_turn_base_7/8 翻负）。

## 解剖：首步修好也救不回（cfg-0002）

S1 首步 `search_text`（S0 是 web_search）→ `read_file` ×3 全部成功、证据到手 → `data_query` 参数错（B2）→ 同一调用重复（B4）→ 强制收尾 → answer 阶段复读 ×2 → 空输出。链 A 在信息源正确时照样完成处决——修首步不修下游。
