## 0. 前两轮结论的处理

本轮复核后，以下旧结论**推翻或待定**，不再作数：

- **推翻**「DeepSeek 协议违规率 81%」：native 通道的结构化调用被文本协议重复计数（165/206 step 被误标 `tool_envelope_missing`+`envelope_recovered`）。修正口径后本轮实测 0.5%（198/199，native_protocol_validity）。
- **推翻**「DeepSeek nt 系列结构性不可通过是模型行为」：那是 harness 每题第一步 `tool_choice: required` 所致（v2 nt-0001 step1 实测 `required`，本轮 `auto`）。修复后结构性阻断消失：本轮参照跑 nt-0001 零调用直接作答（挂在答案带单位 `9000 MiB per hour`，真格式问题），nt-0002/0003/0004 挂在模型自己多调了工具（真 OVERCALL），均为真实模型行为而非 harness 锁死。
- **推翻** v1 的 G1K 分数与「地板效应」讨论：v1 全部 run 受 2 分钟默认 case 超时污染，本轮复现了同一陷阱（并发 40 下首版矩阵 22–24/40 题超时作废），全部作废重跑。
- **待定（本轮实验未证实）**「G1K answer 阶段复读上一条 tool_call 由连续 User 消息诱发」：见 §3。
- v2 的 G1K「收尾纪律缺陷」现象本身（answer 阶段复读）在本轮干净测量下**依然存在且稳定**，但它不是由连续 User 消息引起的。

## 2. Part B：变体定义与实验有效性

实现为 wire 轴 `usermsg`（产品默认 `split` 字节不变，全部旧 golden 原样通过）：

| 代号 | profile 修饰项 | 定义 |
|---|---|---|
| V0 | （无） | Part A 修复后的基线 |
| V1 | `+merge-users` | 任何 `Assistant:` 前最多一条 User（nudge/拒绝说明/answer 指令并入 tool_response 所在 User） |
| V2 | `+merge-users-no-nudge` | V1 去掉每步 nudge 整段 |
| V3 | `+merge-users-rewrite` | V2 + answer 阶段入口回滚被拒/违规输出及其回执、System 换成无目录纯文本作答块、只留一条 User 收尾 |

- golden 渲染测试：`internal/agent/user_merge_golden_test.go`（`TestUserMergeV1Golden/V2/V3`），逐字节断言三次关键生成（工具后、拒绝后、answer 阶段）+ 每次生成断言 ≤1 连续 User。
- 轨迹检查：`tools/check_user_runs.py`。全部 9 个变体 run（3 套件 × V1–V3）**零违规**；v2-g1k-k0 上报 131 处违规（对照有效）。
- 渲染偏差披露：渲染器 `CleanChatText` 会折叠 User 文本内空行，所以 V1 的 nudge 与 `</tool_response>` 之间是单换行而非任务书示例的空行；实验变量（连续 User 数）不受影响，split 路径字节不变。

跑分口径：RWKV `rwkv-g1k-7b-temp-3601` @ `http://100.64.0.1:18222/v1`，贪心（`top_k=1, temperature=1, top_p=1, penalties=0/0/1`——top_k=1 时温度不参与，与历史贪心 run 同约定），单跑，`--case-parallelism 40`，`--max-steps 10`，`--case-timeout 30m`。DeepSeek `deepseek-v4-flash` 只在 workbank 跑 V0（native 通道；`temperature 0.3`，decision/answer 预算 4096/2048 对齐 v2）。

## 4. 判定

按预定规则：V1–V3 与 V0 在 workbank 差距 0 题（≤2），answer 收尾率无改善（11.8%→10.8%→10.5%→0%），**结论：连续 User 假设未被证实，不选胜出变体**。

更强的否定证据（V3）：transcript 已做到零连续 User、回滚了全部被拒输出、System 无工具目录、单条收尾指令——复读反而最重（87.2% 复读率、0% 收尾）。step 级证据：`closeout-v3-g1k` log-0002 step6 answer 阶段，prompt 已是干净形态（checker 验证），模型原始输出仍逐字节输出 `<tool_call>{"name":"count_lines",...}</tool_call>`（还是个未知工具名），step7 再复读一次直至触顶。

新的方向性观察（未归因，留下一轮）：answer 阶段的吸引子不是「最近的 User 块结构」，而更像是 transcript 里自己的 tool_call 历史本身——V3 回滚被拒输出后，模型转而复读更早的成功调用或编造新调用（earlier-call 复读从 V0 的 0 升到 V3 的 6/39）。bfcl-product 上 V2/V3 失分集中在 recovery_multi_turn（多轮恢复类），与 usermsg 变体改变拒绝回执形态一致。

噪声底：贪心下并发扰动（40→8）对 V0、V1 各跑一次：题级翻转均为 **0**。本轮变体间差距（0 题）小于任何可测噪声的说法不成立——差距就是零；同时 workbank 失败模式对并发扰动稳健，不是刀尖 token。

## 7. 下一轮建议（不在本轮范围）

1. answer 阶段复读的真正诱因：建议实验方向——decision 阶段成功调用的 tool_call 在 transcript 中的呈现密度/位置，或 answer 阶段直接 prefill 文本开口（fake think 叠加留待此之后）。
