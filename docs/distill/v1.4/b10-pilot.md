## 6. 给 M3 放量的口径（这批试出来的）

1. **判据**
   - 诱饵值只放进 `output_excludes`，并且必含项要能单独排除诱饵答案；解释性提及（「不走默认的 429」）要么允许，要么在简报里明说不许复述。
   - 数字答案考虑英文拼写（three）。
   - 「写不了 / 查不到 / 没核实」类词表要按真实说法写全，例如「没法创建」「只读」「couldn't」「unchanged」。
   - 长度上限统一用 §4.2 的 600。
   - M8 不要附带 web_fetch 之类与本类无关的硬要求。
2. **判分器管不住、必须人读的四类问题**（本批 4/70）：凭记忆报外部会变的事实、把推测当事实给替代数据、同参数重复调用、取原始行后心算。放量时每条终答都要读一遍，不能只看 PASS。
3. **出题**
   - 用 data_query 的题要按它的真实能力出：只支持等值过滤、没有日期归一。阈值或日期范围题的标准路径是「分组 → 挑组 → 计算器」。
   - 判分的答案值不能恰好是 fixture 里某个无关的字面量（如日期里的 29、36），否则 `bank verify` 的破坏测试检测不到篡改。
   - CSV 字段含逗号（`Mar 11, 2026`）要加引号。
   - 全 `.md` 工作区里 README 会被破坏测试先删首行，verify.py 要校验它。
4. **§3.6 要求的「data_query 列名写错 → 看报错 → 改对重查」占 ≥1/4**，盲解很难保证。本批只有 tab-8005 一条是自然出现的。放量时要么出列名不直观的题，要么接受这一项达不到并在报告里写明。
5. **解题者看不到失败原因**（step.py 设计如此，防止泄题），所以复判分必须由主控重放来做。可以直接用本批的做法：把 solve 状态写成 script、跑 `agent-eval --script` 读 summary 里的 failures。
