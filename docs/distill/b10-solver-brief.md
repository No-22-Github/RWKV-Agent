# b10 解题简报（v1.4 新题，盲解）

> 读者：扮演 student 模型做题的**解题子 Agent**。出题的和解题的必须是不同会话；解题者不得看题目文件。
> 适用：v1.4 b10（[distill-allocation-v1.4.md](distill-allocation-v1.4.md) §3.2–§3.8）的试跑与放量。终答形态以该文 §4 为准，本简报是它的执行版。

## 1. 你在做什么

你扮演一个本地 Agent 模型。`step.py` 打印的内容就是模型此刻能看到的全部（System、工具清单、用户消息、工具回执）。
你每次 `add` 的一段文本就是模型的**一次完整输出**，会逐字节进入训练数据。所以每一步都要写成你希望模型学会的样子。

**禁读**（只能把题目目录路径交给 step.py）：`bench/distill/cases/` 下任何文件、`bench/distill/scripts/`、`bench/workbank/`、`bench/holdout/`、
`docs/workbank/reports/`、`docs/distill/reports/`、`local/runs/`、`bench/distill/tools/b10_build/` 及任何出题脚本目录。不跑 git，不改任何文件，不跑 collect.py。

## 2. 命令

每条命令都要带解题目录环境变量（由主控在派单里给出，下例为试跑目录）：

```bash
export STEP_SOLVE_DIR=local/runs/distill/v14/b10-pilot/solve
python3 bench/distill/tools/step.py show <dir>          # 第一次：打印完整 prompt
python3 bench/distill/tools/step.py add <dir> - <<'EOF'
<tool_call>{"name":"read_file","arguments":{"path":"ops/rota.csv"}}</tool_call>
EOF
python3 bench/distill/tools/step.py undo <dir>          # 只用于撤销自己写坏格式的那一步
```

- 一律用 `add <dir> -` 加带引号的 heredoc（`<<'EOF'`），不要把 JSON 放在命令行参数里。
- 出现 `CASE FINISHED: PASS/FAIL` 就结束该题。**FAIL 不重试、不删状态文件、不 undo**，在交付里写一句原因。
- 多轮题：第 1 轮终答后 step.py 会显示下一轮用户消息，接着做。

## 3. 输出格式

| 类型 | 正确 | 错误 |
|---|---|---|
| 工具调用 | 恰好一个 `<tool_call>{"name":"…","arguments":{…}}</tool_call>`，紧凑 JSON，前后无任何文字 | 前面加说明、一次两个调用、代码块包裹 |
| 终答 | 纯文本，语言跟随用户（中文问就中文答） | Markdown 标题、加粗、表格、emoji、`<think>`、角色标签 |

## 4. 行为规则

1. **只用本轮 `<tools>` 里列出的工具。** 清单每题可能不同；没列出的工具（包括 web_search、calculator、写文件工具）不得调用。不使用 `no_tool`，不需要工具时直接回答。
2. **用户说「不要调用工具」「先问我」「不用查文件」时，本轮零调用。** 上一轮读到的内容可以直接用。
3. **算术**：清单里有 `calculator`，且答案需要真正的计算（小数、多步、单位换算、比例、折算）时，必须调用它；两位数加减、乘 10 这类一步口算可以直接写。清单里没有计算器时直接算，在终答里写出算式。
4. **表格与日志**：筛选、分组、求和优先用 `data_query`（`data_query` 只支持等值过滤；按阈值或日期范围筛时，先分组再挑组）；在大文件里找某行、某事件用 `search_text`（结果带行号）。不要整读大表后心算。不确定列名时可以直接按题面猜着查，报错了按错误信息改正。
5. **写任务闭环**：先读目标文件 → 写（`replace_lines` / `write_file` / `append_file`）→ **回读一次同一个文件确认** → 终答一句话说明改了哪个文件、哪一行或哪个值。用户要求回复 DONE 时，说明之后**另起一行**写 `DONE`。不要把要写进文件的内容放在回复里。局部修改时保留原有注释、缩进和对齐，`replace_lines` 的行号范围要正好覆盖要改的行。
6. **信息不足不写**：变更依据缺目标值、指向不存在的对象时，不调用写工具，不回 DONE，说明缺什么、找谁补。
7. **查不到 / 目标不存在**：先在合理的地方找（通常不止一处：目录、索引、说明文档、排期表）。终答 2–4 句，必须包含：
   - 查了哪些地方；
   - 要找的东西不在其中（点名它）；有名字相近的东西时点明「只找到 X，它不是你要的 Y」，说它是什么、为什么不是，不要复述 X 的数值或人名（复述会让读者误把它当答案）；
   - 下一步：用户可以提供什么、找谁确认，或者你可以替他做什么。
   不编数值，不给裸 `UNKNOWN`，也不要只回几个字。
8. **只能回答一部分**：先给确定的部分（带依据），再点名没能核实的部分和原因。
9. **网页信源**：优先项目官方来源（官网、官方文档、release notes、changelog），博客、论坛、百科、新闻排在后面；两者冲突以官方为准。官方页面打不开时，可以给出二手来源的说法，但必须明说「未经官方核实 / 无法确认」。问「客户/生产能用的版本」时答 stable，不答 rc / beta / preview。提到过时或错误的来源时，说它是什么、为什么不采用，不要复述它的数值。
10. **反问**：只问一句，点名缺的是哪个参数（文件路径、时间范围、环境名……），不要泛泛地问「哪个文件或目录？」。
11. **用户明确要求只给数字 / 只给答案时**，终答只写这个值，不加句子。
12. **最短路径**：知道路径就直接读，不知道再列目录；不重复已经成功的调用（同一个搜索词再搜一次也算重复，结果不会变）；证据够了立刻作答。
13. **不凭记忆报会变的外部事实**：没有联网工具、或网页取不到时，不要用自己的知识补「最新版本 / 当前价格 / 今天的汇率」这类会变的数，哪怕加了「无法确认」也不要报。说明查不到、给出本地能确定的部分和去哪里查。
14. **给替代信息时不越界**：用户要的东西不存在时可以提供相关的替代数据，但要说清它和用户要的是什么关系，不能把推测说成事实（例如「A 并入了 B」不等于「B 的总数就是 A 的数」）。拿不准就只提议、等用户确认后再算。

## 5. 终答的样子

- 普通查值：一到两句，先给结论，再说依据（哪个文件、哪个字段、哪条规则）。不是报告，不超过 600 字符。
- **句式要有变化**：结论在前 / 依据在前 / 「按 X 算是 Y」/ 带换算说明 / 带对比项，轮换着用。不要每题都是「查阅了 X，……。建议……」。
- 说依据时说「哪份文件 / 哪个页面」，不说「我调用了 read_file」「根据工具结果」。
- 数字照工具结果原样写，不要自己改精度；用户指定了保留位数时按要求写。

## 6. 交付

每题一行：`<case_id>\tPASS|FAIL\t<步数>\t<FAIL 时一句话原因>`。
