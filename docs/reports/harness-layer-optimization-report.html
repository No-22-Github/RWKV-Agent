TL;DR · 三句话

如果只看三点

01

分数上升几乎全来自 Harness，不是模型

有一次只改 Harness、模型没动的对照：boundary 8→10、答案 9→12、工具错误 29→16，而模型调用还是 91 次没变，排除了靠多花预算刷分。

02

一条纪律：不写题目特判

改的都是通用 Runner 规则、工具边界和判分语义，没有关键词路由，也没有按 case 打补丁。这样分数才可信，失败轨迹拿给模型团队也才有用。

03

差距已经从「控制面」挪到了「答案正确性」

对比成熟 API 模型，路由、必需工具、必需调用、禁用工具规避全部满分打平。剩下的 5 题差距里，只有 2 题是真实推理能力，其余仍是 Harness / 判分口径可动的地方。

Why · 分数为什么会涨

三个来源，按诚实程度排序

重点不在涨了多少，而在凭什么说这是真提升。三个来源都能用 trace 独立验证，也都和模型能力分开记账。

1

Harness / 工具契约修复（模型权重没变）

很多「工具错误」不是模型的锅：畸形路径被当成了真实观察、名义绝对路径 /workspace/… 没归一化、不合身的工具在生成错误答案。这些修完，同一个模型就把编造的答案变成了正确事实。

2

判分语义修正（尊重有效路径）

把 list_files / search_text 这类发现动作当成一个等价类：一次 search_text 就完成「搜到文件 + 读到值」两步工作时，不该因为没走 rubric 指定的固定序列而判失败。这修的是判分器口径，不是模型。

3

有界收束把「不会停」的模型也接住了

模型学不会「证据够了就停」——18 题里 14 题靠 Harness 强制进入回答阶段。重复调用拒绝、连续失败限流、预留最终回答 step，让「不会停」不再等于「没有答案」。

17 个可以直接抄走的 Harness 招式

每张卡片顶栏是代码锚点（file:line 或测试名），下面按 问题 / 做法 / 为什么 / 抄作业 排。只挑换个项目也用得上的，纯机械的实现细节不列。

A

让弱模型稳定产出合法控制帧

续写式后端（不是原生 function calling）要让模型「开对帧」并不容易。做法是用 prefill 替模型把最容易出错的那步定死，并让 prefix 对齐 tokenizer 的真实边界。

internal/inference/prompt.go:73协议

半 tag：prefill 停在 <think，把最后一个 > 留给模型

问题
给 prompt 补上「看起来完整」的 <think>，续写质量反而崩。
做法
prefix 结尾故意停在 <think（不带 >），由模型自己生成 >；解析前用 reconstructOutput 把前缀补回。
为什么
RWKV tokenizer 把 > 和其后文本合并切分，…<think 与 …<think> 的尾部 token 序列不同。补 > 会让续写从训练分布里不存在的 token 边界开始。
抄作业
prefill 必须停在训练时真实出现过的 token 边界，别按「肉眼完整的字符串」补全。TestFastThinkingRendererUsesExactTokenBoundary 锁死这条约定。
internal/agent/protocol.go · ToolPrefix协议

首个工具动作预填 <tool_call>，模型只补 JSON 尾部

问题
让模型自己决定「要不要开帧 + 开什么帧 + 填什么参数」，一步错步步错。
做法
inspect 路由首次动作把 <tool_call> 作为 assistant 前缀预填；模型只生成受约束的 JSON 尾部，Runner 重建完整 frame 后做严格 envelope/JSON 解析。
为什么
把「开帧」这个高频失败点变成确定性的框架动作，模型的自由度收窄到它真正该负责的内容上。
抄作业
凡是「格式对错」和「内容对错」耦合的地方，用 prefill 把格式那半拆出来交给框架。
internal/agent/runner.go · 第一轮放行纯文本协议

混合门控：只有以 <tool_call> 开头的输出才进严格帧解析

问题
强迫每一次输出都走严格 JSON envelope，会把「本可以直接回答」的简单轮次也逼进协议错误。
做法
第一轮允许普通文本直接回答；只有以 <tool_call> 开头的输出才进入严格控制帧解析。文本 final 与 G1I 工具控制帧是联合输出语义，共用一套提交边界。
抄作业
协议严格度要「按需触发」，不是「全程开启」。给不需要工具的路径留一条低摩擦通道，协议合规率和体验都会更好。
B

不让模型假装完成

答案的真实性由宿主的确定性规则保证，不靠 prompt 请求模型自觉。关键是把「拿到可信观察」和「没拿到」在事务层面分开处理。

internal/agent/runner.go:606, 981证据

没有证据就不提交：ErrNoWorkspaceEvidence + 事务回滚

问题
模型工具全部失败，却照样编一个答案交上去（例：幻觉出 --migration-flag=2.4.0）。
做法
inspect 轮若有过工具尝试但没有任何可信观察，直接以 ErrNoWorkspaceEvidence 失败并回滚整轮，不生成、不提交无证据答案。
抄作业
「答案的前提是有可信观察」应当是一条硬约束，而不是 prompt 里的一句请求。
internal/agent/runner.go:695证据

证据可信度分类：参数错误 ≠ 真实观察

问题
畸形路径报错（裸 fmt.Errorf）被当成「到达过工作区」，点亮了 hasToolEvidence，让回滚失效。
做法
toolEvidence := !errors.Is(err, ErrInvalidToolArguments)：工具触达世界之前被拒的参数错误不算观察；缺失文件（lstat）和运行时失败触达了世界，仍算可信观察。越界拒绝本身也算可报告的观察。
抄作业
给每一类工具错误明确归类：「还没碰到世界就被参数校验拦下」和「碰到了世界然后失败」是两回事，只有后者能作为回答依据。
internal/agent/protocol.go · 最终答案泄漏校验提交

提交前拦截协议泄漏；确定性弃答，但把模型原文留给判分

问题
模型把协议标签、role header、整段 JSON、原始工具 payload 直接当答案输出给用户。
做法
提交前拒绝这些泄漏；写进用户 transcript 的是确定性弃答，但模型原文仍单独保留给 answer_accuracy，「答案契约修复率」单列统计。
抄作业
安全兜底和能力度量要分账：别让安全修复悄悄掩盖模型的真实弱点——否则你会以为模型变好了，其实是兜底在替它答。
C

有界收束，把失败当成正常路径

Agent 循环常见的三种翻车：无界重试、上下文越滚越脏、跑到 step 上限交白卷。下面几条给每种情况一个确定的出口。

internal/agent/runner.go · 重复/限流/预留收束

重复调用拒绝 + 连续失败限流 + 预留最终回答 step

做法
精确重复的调用（无论成功失败）直接拒绝、不执行；同一工具连续失败最多实际执行两次，第三次阻断；任意工具尝试后都预留一个最终回答 step。
为什么
模型学不会「够了就停」，那就让「不停」也不会掉进 step 超限的空答案坑：证据不足时收束为「明确限制」，而不是交白卷。
抄作业
为「模型不肯停」设计确定性出口，比把 MaxSteps 调大有用得多。
ErrUnclosedThink / ErrOutputTokenLimit收束

Correction 要对症：失控推理 → 立即 </think>

问题
未闭合 <think>、输出预算耗尽，全都笼统归到「envelope 缺失」，纠错提示牛头不对马嘴。
做法
拆成独立 sentinel（route 侧对应 ErrRouteTokenLimit），按错误类型分派 Correction：失控思考被要求立即输出 </think> 并禁止重开推理。
抄作业
通用「格式错了，重来」对失控推理无效。先把失败原因分类，再让纠错提示针对那一类。
internal/agent/runner.go · retryEcho收束

协议重试不把失控原文回写进上下文

问题
重试时把上一轮的失控推理原文写回 transcript，第二次重试在更脏的上下文里以同样方式再失败。
做法
重试时丢弃失控原文（retryEcho），decision 和 route 两条重试路径都修。
抄作业
重试的前提是「上下文比上次干净」，否则重试只是把同一个坑再踩一遍。
internal/agent/tools.go · /workspace 归一化恢复

名义绝对路径归一化：给出正确形状，而不是连试 5 次

问题
模型看不到真实临时目录根，/workspace/x 是它最合理的猜测，但旧文案不给正确形状，它就连试 5 次直到预算耗尽。
做法
把名义绝对路径映射成候选相对路径，只接受归一化后确实存在于工作区内的候选；错误文案直接给出修正后的路径形状。/etc/hosts 等真实越界照旧失败。
抄作业
工具报错的第一职责是「让下一次调用能成功」——把正确形状写进错误信息，比拒绝更有用。
D

让实验可归因

greedy 解码下，prompt 是唯一能解释输出变化的输入。不记录 prompt、不还原收尾原因，分数一变就只能靠猜。

rwkvlightning/client.go:470 · inferFinishReason度量

自己推断 finish_reason：否则协议合规指标整条是错的

问题
服务端不返回 finish_reason。max_tokens 截断被误报成协议格式错误；启用服务端 stop 后 stop 序列被吃掉，FinishUnknown 会把正确的 <route>inspect 判成未闭合信封——实测直接打成 route 0/18。
做法
客户端自行推断：生成 token 达到预算记 FinishLength；低于预算且有输出记 FinishStop。
抄作业
接非流式 / 无 usage 的后端时，收尾原因必须自己从 token 数补出来，否则「协议合规率」是个假指标。
Step.Request · TracePromptBytes度量

trace 记录 prompt 粒度：完整 prompt + 字节数 + 工具清单

问题
旧 trace 只记 model_output。greedy 下换了工具清单分数就动，但无法归因到底是哪一处 prompt 变化。
做法
记录每次生成的完整 prompt、字节数、assistant 预填、stop、max_output_tokens，以及 decision 阶段的工具清单；并新增路由每一次尝试的 prompt/输出/解析错误。
抄作业
greedy 评测里不记 prompt 就没法归因。同参数复跑逐项一致，证明「记录本身不改变行为」。
受控单题 A/B · pb_missing_file_recover度量

用 prompt trace 证实：分数漂移的真凶是「工具清单变化」，不是能力退化

证据
唯一差异是工具注册表：decision prompt 2622 → 2263 字节，在第 1505 字节首次分歧，差异正是 structured_query 那 359 字节说明行。首个动作因此从 search_text{case_sensitive:true} 变成 {case_sensitive:false}，两者答案都对，只是后者不再经过 rubric 要求的 list_files。
抄作业
工具清单以 Available tools: 段落渲染进每一个 decision prompt——所以撤掉一个工具会连带移动所有 case 的轨迹，哪怕它从不调用那个工具。任何改工具清单的实验，都要同时记录工具清单和 prompt 字节数。
E

做减法：一次撤工具，一次撤阶段

两次删除都在 RWKV7 G1i 13B 上实测过。前提是先有了 prompt trace，能确认删掉之后分数确实没退，否则不敢动。

撤掉 structured_query · v8→v9减法

不合身的工具，比没有工具更差

问题
structured_query 表达不了多指标 / 列选择 / 跨表；有它时给出 355.72（应 438.72）、$1,499.50（应 1248.50）。
做法
把它从 boundary 撤出、ComputeTools 收窄为仅 calculator；任务改由 read_file + calculator 组合完成。
为什么
撤掉后仅用 read_file 两题就答对了，连 calculator 都没用——模型自己的算术本来是对的。是那个不合身的工具在主动制造错误答案。
抄作业
注册工具前先问「它能不能完整表达任务」。一个只能部分表达的工具，会把模型拽进「可执行但语义错」的答案。
--route-stage 默认关闭 · v11减法

撤掉整个 route 阶段：更省、更稳、分数不退

问题
route 是早期给小模型的引导脚手架，每轮多花一次模型调用。
做法
RWKV7 G1i 13B 上改为默认关闭：boundary 13/18 不变，模型调用 69→48、耗时 345s→250s、协议 96.1%→100%；assistant 2/6→3/6。
为什么
assistant 唯一变好的那题，模型行为本就正确（正确追问、零工具调用），只是被 route 断言误判成失败——这个阶段成了它自己的唯一失败来源。
抄作业
脚手架要能一键关、并且对够强的模型默认关。判分也要跟着改：阶段不跑时若照常计分会白送 100%，用 manifest 里的 route_stage 字段控制。
F

判分尊重有效路径，双口径记账

判分器自己会制造假阴性。要把它当成一个变量，和模型能力分开记。

eval/runner.go:558 · discoveryTools判分

发现类工具等价类：一次搜索完成两步，不算失败

问题
v9 下多题答案完全正确，只因没走 rubric 指定的 list→read 固定序列而失分。
做法
把 list_files / search_text 视为一个等价类：required_tools 的发现要求可由任一发现工具满足，required_calls 允许复用已匹配步骤；非发现工具（calculator 等）仍严格按名匹配。
抄作业
rubric 要奖励「达成目标」，不是「复述我设想的路径」。强制固定序列会惩罚更省的解法。TestBoundaryScoringAcceptsEquivalentDiscoveryPaths / ...StillRequiresInvestigation 一起守住边界。
效果
RWKV 10/18 → 13/18，DeepSeek 13/18 → 17/18，两侧无新增失败。
answer_accuracy vs task_success判分

严格分和语义分都报，不只报一个

问题
模型事实全对，但附了解释、或日期写成中文格式，被严格字符串判分打成失败。
做法
同时报严格口径（如 10/18）和语义口径（如 ~14/18），并把「答案契约修复率」单列。ISO / 中文日期、「不可用」降级措辞都接受二选一。
抄作业
「格式没遵守」和「事实答错了」是两种失败，混在一个数字里会误导模型训练的优先级。

Principles · 可迁移的原则

换个项目也成立的六条

01

真实性靠 Controller 强制，不靠 prompt 请求。「没有可信观察就不许提交答案」要写成硬约束和事务回滚。

02

先能测准，再谈优化。greedy 下记录 prompt 粒度 + 自推 finish_reason，否则协议合规率和归因全是假的。

03

工具错误要分类。「碰到世界前被拒」和「碰到世界后失败」是两回事，只有后者是证据。

04

不合身的工具比没工具更差。它会把模型拽进「可执行但语义错」，注册前先确认它能完整表达任务。

05

为「模型不肯停」设计确定性出口。重复拒绝 + 失败限流 + 预留回答 step，比调大 MaxSteps 有用。

06

判分器是变量，双口径记账。奖励「达成目标」而非「复述路径」；严格分和语义分都报，别用总分盖过锅。
