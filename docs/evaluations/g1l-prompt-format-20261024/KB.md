# RWKV G1L Agent 提示词、工具格式与采样：结论与建议

- 日期：2026-10-24
- 适用模型：RWKV-7 G1 系列，结论以 G1L 预览版 `rwkv-g1l-7b-temp-3797` 基模（无 State、无微调）为准
- 依据：完整 Agent 考卷（agent-exam-v1.2，568 题，中英各半）上的三轮消融加一轮复核，17 组配置、40 遍、22,720 道题次

## 一、核心结论

1. **生成点写 `Assistant:`，冒号后不能带空格。**
   多一个空格，通过题数从 175 降到 112（−36%），英文题 97.8% 的输出变成中文作答。
   原因在分词器：`:` 和空格是两个独立 token，英文词会把前导空格并进自己（` Hello`），尾随空格迫使模型生成训练中几乎没见过的"无前导空格"的词。

2. **接受"先说一句话再调用"是最大的单项收益。**
   G1L 习惯先写"我先查一下……"再输出工具调用。默认解析器把这种输出当成终答；打开 `recover-preamble` 后，通过题数从 123 涨到 175（+42%，p≈5×10⁻¹²）。

3. **基模上不开思考、不合并 User 消息、不用旧的围栏写法。**
   快思考 −23 题，完整思考 −28 题；合并连续 User 消息的三种写法 −10 到 −17 题；旧的 ```` ```json ```` 围栏产品写法 −68 题。

4. **采样用 `agent-fast`**（T=0.3、top_p=0.5、presence 0.5、frequency 0.1、decay 0.996）。
   去掉惩罚、贪心、T=1（含官方 demo 默认值）、加重惩罚都更差（−12 到 −28 题）。轻度重复惩罚是正收益，也不会把工具调用的 JSON 写坏。

5. **官方风格的精简系统提示总分更高，但它是取舍，不是全面更好。**
   `System: Tools:` 开头、两条规则、无示例：4 遍均值 177.5 对 169.25（+8.25，p=0.029）。
   代价是模型更少调用工具：直接作答类几乎翻倍（29 → 57），本地读取类 −13 题（p=0.013），外部信息类 −9 题。

6. **头号失败原因是"重复上一次成功的调用"，提示词解决不了。**
   53% 的题出现"重复 → 被拒 → 强制收尾"，这些题通过率只有 20%（其余 43%）。被重复的结果并不长（中位 165 字符），56% 是紧接上一步原样照抄。
   删除或移动提醒、换采样、换提示词，最多只能压低约 20%。

## 二、建议

### 默认配置

| 项 | 建议 | 依据 |
| --- | --- | --- |
| 解析 | `agent-wire-v1.0` 默认打开 `recover-preamble` | +52 题 |
| 采样 | 评测与 App 默认都用 `agent-fast`（App 现为 `agent-default`） | 去掉惩罚 −17 题 |
| 生成点 / 思考 / User 分写 | 保持现状：`Assistant:` 结尾、不开思考、工具结果与提醒分成两条 User | 见结论 1、3 |
| `no_tool` 出口工具 | 保留 | 去掉后 −12 题，重复调用 +30% |
| 系统提示 | 按产品取向选：以"先查再答"为主用默认提示；希望闲聊少误调用工具用精简提示 | 见结论 5 |

系统提示建议先再测一个折中版：精简提示加回一句多步规则（"拿到工具结果后，只在缺具体事实时再调用，否则直接回答"），检验能否两头兼得，再定默认值。

### 训练数据

1. 先定默认格式，再按它渲染训练数据，保证训练与推理字节一致。
2. **重点补"拿到结果即作答、不重复调用"的示范**——这是提示词和采样都解决不了的部分。
3. 若采用精简提示，需在数据中补足多步读取的示范，弥补本地读取类的下降。
4. 训练片段从 `Assistant:` 之后开始，把空格划进训练片段；终答片段带终止符（见第三节）。

## 三、Prompt 书写规则

### 3.1 分词：先搞懂这几个切法

RWKV World 词表（`rwkv_vocab_v20230424`）是贪心最长匹配：

| 文本 | 切成 | 含义 |
| --- | --- | --- |
| `Assistant: Hello` | `Ass` `istant` `:` ` Hello` | 冒号单独一个 token；英文词带前导空格 |
| `Assistant: 你好` | … `:` ` ` `你` `好` | 中文前的空格是单独的 token |
| `Assistant: <think` / `: {` / `: ```` | … `:` ` <` / ` {` / ` ``` ` | 空格并进后面的符号 |
| `\n\n` | 一个 token（id 261） | 块分隔符本身是一个 token |
| `User` | id 24281 | 可作整数停止 token |
| `<think></think>` / `<tool_call>{` | … `></` / `>{` | `>` 会和后面的字符合并 |

词表中没有 `: ` 这个 token，所以 `Assistant:` 与后续内容永远在冒号后断开。
中文正文不受尾随空格影响，但工具调用的 ` <`、JSON 的 ` {` 会被拆开，所以中文题同样会掉分（实测 −30 题）。

### 3.2 生成点与种子

- prompt 以 `Assistant:` 结尾，什么都不加，第一个 token 让模型自己生成。
- 可以接**训练中真实出现过**的种子：`Assistant: <think`、`Assistant: ```json`、`Assistant: {"answer": `（官方材料问答，这里的尾随空格是有意的）。
- 判断标准：**种子的最后一个 token，在训练文本里是否也是一个独立 token**。

| 预填 | 结尾 token | 是否安全 |
| --- | --- | --- |
| ```` ```json\n ```` | `\n` | 安全 |
| ```` ```json\n{"name":" ```` | `":"` | 安全 |
| `根据上面的工具结果，` | `，` | 安全 |
| `<tool_call>` | `>` | 不安全：训练里是 `>{` |
| `<think></think>` | `>` | 不安全：应写 `<think></think` |

### 3.3 块结构

```
System: ...

User: ...

Assistant: ...

User: ...

Assistant:
```

- 块之间恰好一个空行；块内容里不能有空行（`\n\n` 会被当成块结束）。官方建议先清洗 System / User 文本：
  `re.sub(r'\n{2,}', '\n', txt.replace('\r\n','\n')).strip()`。Assistant 文本是协议载荷，不清洗。
- 标签区分大小写，后跟一个半角空格：`System:` `User:` `Assistant:`。
- `System:` 只有一个，放最前面。
- token 0 是文档结束（EOS）。基模常常不发 EOS、直接续写下一轮，停止条件要同时给 `0` 和 `User`（24281），或文本 `\n\nUser:`。

### 3.4 思考模式

合法写法只有三种（小写、逐字，都不带最后的 `>`）：`Assistant: <think`（完整思考）、`Assistant: <think></think`、`Assistant: <think>\n</think`（官方"假思考"）。
控制思考长度：在用户文本末尾加 `(think)` / `(think a bit)` / `(think a lot)`。
即使不开思考，G1 系列也常自发写 `<think>`，解析器要能剥掉。基模 Agent 场景下开思考更差（结论 3）。

### 3.5 工具调用

官方 G1x 模板：

```
System: Tools:
[
{"name":"find_free_slots","description":"…","arguments":{…}},
…
]
Return only a JSON function call.

User: …

Assistant: ```json
{"name":"find_free_slots","arguments":{…}}
```

User: Function output:
{…}

Assistant:
```

官方要点是"keep it concise"。本仓库默认用 `<tool_call>{…}</tool_call>` 信封、`<tools>` 清单、`User: <tool_response>` 回传结果；
实测中，官方的"`Tools:` 开头 + 精简规则"可以和 `<tool_call>` 信封组合使用（结论 5），旧的围栏产品写法不可用（结论 3）。

### 3.6 经验要点

- **改提示词先看行为分布，再看总分。** 两种提示总分接近时，做对的可能是两批不同的题。
- **RWKV 会照抄自己上一回合。** 刚输出过工具调用，下一步很容易原样再来一次；作答阶段重试时，不要把被拒的调用再放回上下文。
- **提示里的语言会带偏输出语言。** 尾随空格那组英文题全变中文；系统提示中固定的中文说明也可能拖累英文题（未单独测）。

### 3.7 历史经验（G1K 及更早，仍可参考）

| 经验 | 来源 |
| --- | --- |
| 预填锚点深度决定 `arguments` 形状：只预填 ```` ```json\n ```` 时约一半写成字符串，预填到 `{"name":"` 时为 0 | 2026-08 G1I |
| 系统提示里的示例块是负资产：去掉示例 + 一阶段作答 + `no_tool` 出口，bfcl-product 40 → 49/60 | 2026-09 G1K |
| 带思考的模型要给足决策预算，否则测出来的是 harness 而不是模型 | 2026-08 / 09 |
| `top_k=1` 时温度失效；截断（top_p）比温度更重要 | 2026-09 G1K |
| 终答训练片段必须带终止符，否则答完会续写 `✿text1✿` 或下一轮 `User:` | 2026-09 |
| 空搜索结果附一句中文说明（"同样的关键词再搜也不会有结果"）最好；英文 "tell the user…" 会被原样当终答 | 2026-10 |
| 长网页：总结约 12K token 内健康；问事实时 6K 以后正确率掉到 2–4 成 → 6K 截断 | 2026-10 |
| Hermes Agent 轨迹格式在 G1K 上全军覆没：拿到结果后不写答案、一直调用 | 2026-10 G1K |

## 四、实验概要

### 4.1 设置

- 端点：内网 8018 网关（albatross-1.3.0），每轮前后快照，模型与引擎版本全程一致。
- 考卷 agent-exam-v1.2（568 题），App 实际配置（`--harness app`），scorer-v4，harness v23。
- 每组 2 遍，两个最终候选 4 遍；总并发 64。40 遍全部通过参数闸门，0 道作废。
- 判定：逐题配对 + 双侧符号检验，p < 0.05 且各遍同向才判有差异。参照组 `rp` 共 6 遍，得分 167–178。

### 4.5 重复调用分析

最初的假设是：每步工具结果后跟着一条约 53 token 的提醒，把证据推离生成点，RWKV 作为循环结构因此"忘了"结果。验证结果：
- 提醒删掉、挪到结果之前，重复率都基本不变；
- 首次重复的 365 题中，原调用成功 296 次，结果中位 165 字符，206 次紧接上一步；
- 典型例子：模型读到 `hold_queue_depth: 350`（正是所问的值），下一步原样再读同一文件。

结论：这是模型照抄上一回合的惯性，不是上下文距离问题。

## 五、局限

- 每组 2 遍（候选 4 遍），约 10 题以内的差异只能记为"无法区分"。
- 采样只在一种格式上扫，系统提示只在一种采样上测，没有做完整交叉。
- 总分受题型构成影响：直接作答类占 16%，调用倾向不同的配置之间，总分高低部分取决于这个比例。
- 结论只对 G1L 预览版基模成立，训练后的模型需要复测。
