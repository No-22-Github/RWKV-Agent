# 题库构成盘点与整理建议

日期：2026-10-15。这是第一次从「题目」这一层看整个本地题库：有哪些题、各自测什么、有没有偏向某一类，以及外部评测框架是怎么组织题库的。
本文只做盘点和提建议，**题目、判分和跑分脚本都没有改**。数字可用同目录的 [`analyze.py`](analyze.py) 复算。

---

## 0. 先看结论

1. **主考卷 workbank 量够，但偏得厉害。** 148 题全是英文；用户中途追问的题只有 3 道；script 和 tabular 两类共 40 题（27%），RWKV 几乎从来没做对过。
2. **总分的波动大多来自少数几类题。** web 类 16 题在不同模型之间能从 0 题摆到 11 题。两个模型总分差几分时，往往只是这一类题的差别。
3. **其他题集补了一部分短板**（中文、多轮、bash、天气），但它们分散在五六个目录里，名字是按「第几批出的题」起的，不是按「测什么」，读报告时很难对上。
4. **留存题集 p13 从来没跑过**，一直被当作防泄漏的对照面，但手上没有它的任何成绩。
5. 外部框架普遍有三样东西是我们没有的：**一份题集总表**（每套题测什么、怎么计分、算不算主分），**按能力分别出分而不是只报一个总分**，以及**同一道题跑多次看稳定性**。第 5、6 节分别讲外部做法和整理建议。

## 3. workbank 内部构成

**场景**：script 20、tabular 20、logs 17、config 16、web 16，code、docs、hybrid、notool 各 12，filesystem 11。
基本是按出题手册的配额出的（`bench/workbank/tag-vocab.json`），只有 logs 少 3 题、filesystem 少 1 题，是下架造成的。

**难度**：L0 38、L1 74、L2 36，接近手册定的 25% / 50% / 25%。

**能力轴**（一题可标多个）：OBS 66（45%）、CHN 27、DEC 19、VER 16、CON 10、ERR 9、LNG 6、STP 3，另有 17 题没标。

**答案怎么判**：

| 判法 | 题数 | 说明 |
|---|---|---|
| 精确数字 | 56 | 允许误差 |
| 只看文件最后的样子 | 38 | 写脚本、改配置这类，跑 `verify.py` 检查 |
| 精确短串 | 28 | 一个路径、一个版本号之类 |
| 包含关键词 | 22 | 较长的回答 |
| 应当回答 UNKNOWN | 4 | 数据里本来就没有答案 |

**用户轮数与工具步数**：

- 用户轮数：145 题只有一条用户消息，只有 3 题有追问（nt-0010、nt-0012、hyb-0011）。
- 工具步数（按出题时的参考解）：

| 参考解要调几次工具 | 0 | 2 | 3 | 4 | 5 | 6 | 7 |
|---|---|---|---|---|---|---|---|
| 题数 | 12 | 6 | 38 | 62 | 23 | 6 | 1 |

也就是说，「模型连续调好几次工具」这种多步交互几乎每题都有；**缺的是用户中途追问、改需求**。

## 4. 偏倚

### 4.1 workbank 测不到中文

148 题的提问全是英文。实际使用和蒸馏数据都以中文为主，之前「bfcl 一到中文就崩」这类问题，在主考卷上看不出来。
中文题目前只在 p13（没跑过）、bfcl-product 和两个探针里有。

### 4.2 四分之一的题对 RWKV 没有区分度

统计了 2026-10-03 以来本机上所有完整的 148 题跑分：RWKV 88 次（各种 state / 训练点混在一起），老师 2 次（DeepSeek 143/148、MiniMax 132/148）。

| 场景 | RWKV 平均通过率 | 老师平均通过率 | RWKV 一次都没做对的题 |
|---|---|---|---|
| script | 2% | 90% | 13 / 20 |
| tabular | 3% | 97% | 12 / 20 |
| logs | 9% | 91% | 4 / 17 |
| config | 12% | 100% | 5 / 16 |
| code | 10% | 92% | 4 / 12 |
| docs | 13% | 100% | 2 / 12 |
| filesystem | 13% | 100% | 1 / 11 |
| hybrid | 7% | 71% | 2 / 12 |
| notool | 31% | 92% | 0 / 12 |
| web | 34% | 94% | 0 / 16 |

- 全部 148 题里，RWKV 有 43 题一次都没做对，没有一题的通过率超过 90%。
- 按判法看，「只看文件最后样子」的 38 题平均只有 3%，其中 22 题从没做对过。
- 老师在这些题上都是 90% 上下，所以不是题出坏了，而是 RWKV 还没有「写脚本 / 表格计算 / 改文件」的能力。
- 但对比两个 RWKV 版本时，这 40 题基本是固定的零分，不提供信息。

**bash 第二部分也是一样**：v141b-s1224 在其中的 tabular、logs 都是 0/13，聚合类 0/19。换了出题模型、改成中英各半，仍然是零分，可见零分来自「多文件聚合、要精确数字」这类能力本身，跟语言和出题者关系不大。

### 4.3 总分被 web 和 notool 两类题左右

同一套 148 题，三个推荐点按场景拆开：

| 模型 | 总分 | web | notool | tabular | script |
|---|---|---|---|---|---|
| v141b-s1224（work-v1） | 29 | 8/16 | 3/12 | 0/20 | 1/20 |
| MiSS lr3e-5（work-v1） | 26 | **0/16** | **8/12** | 0/20 | 0/20 |
| MiSS lr3e-5（work-v2） | 49 | 11/16 | 7/12 | 4/20 | 0/20 |

前两行总分只差 3 分，但两个模型强项完全不同：一个 web 做对一半、notool 偏弱，另一个反过来。只看总分会误以为两者「差不多」。

> 注：MiSS lr3e-5 在 work-v1 下有两次跑分。01:47 开始的那次是 40/148，后来被移进了 `aborted/`；03:13 重跑的那次是 26/148，和 work-v2 那次同时在跑。上表用的是没被移走的 26。哪一次才算有效，目前没有记录，要先查清楚。两次相差 14 分，本身也说明单次跑分的波动很大，见 6.2 的「跑 3 次」。

### 4.4 有些能力题太少，测不准

| 能力 | workbank 里的题数 | 说明 |
|---|---|---|
| 长输入（LNG） | 6 | 6 题里 4 题 RWKV 从没做对，基本测不出变化 |
| 及时停（STP） | 3 | — |
| 用户追问 | 3 | 别的题集里有，但不进主分 |
| 应当回答 UNKNOWN | 4 | 弃权能力主要靠 bfcl-product 测 |
| 出错恢复（ERR） | 9 | — |

另外有几种任务类型 workbank 里一题都没有：用专用工具（special_tool）、调完工具写产物（tool_then_write）、批量改文件（bulk_edit）、限定范围删除（scoped_delete）、复现脚本输出（reproduce_output）。它们只出现在两份第二部分里。

### 4.5 出题者和老师是同一批模型

workbank 由 GLM 和 DeepSeek 起草，DeepSeek 又是蒸馏老师，在 workbank 上拿到 143/148。两个探针由 Claude 出题。
出题模型的措辞习惯和陷阱设计可能更「顺」它自己，用这些题比较老师之间的强弱，结果偏向出题者。用来比较 RWKV 不同版本时影响较小。

### 4.6 两份第二部分各自偏一类

天气第二部分 30 题里 25 题是 hybrid；bash 第二部分偏 tabular 和 logs（共 26/60）。各自当专项探针用没问题，但不能拿它们的总分去代表「整体能力」。

## 5. 外部框架怎么组织题库和评测

| 框架 | 组织方式 | 值得学的 |
|---|---|---|
| [Inspect AI](https://inspect.aisi.org.uk/)（英国 AISI） | 每个评测拆成四件：数据集（题目 + 标准答案）、Solver（怎么让模型做题）、Scorer（怎么判）、Task（把三者绑在一起）。多个 Task 组成 [eval set](https://inspect.aisi.org.uk/eval-sets.html)，中断后可续跑 | **题目、做题方式、判分三者分开**。我们的题目和工具清单、wire 格式经常绑在一起：跑分脚本给 workbank 写死了 work-v1，可 MiSS 的训练数据 81% 是 work-v2，换成 v2 后多做对 16 题、少做对 7 题。另外 `epochs` 把一题重复跑 N 次，再用 mean / at_least_n 等规则合并 |
| [Terminal-Bench 2.0 / Harbor](https://www.harborframework.com/docs/tasks) | 每题一个目录：`instruction.md`（给模型看的题面）、`task.toml`（作者、难度、类别、超时）、`environment/`、`solution/`（参考解）、`tests/`（验收脚本） | 和我们的 `case.json + verify.py` 很像，**多了「参考解必须真能跑过验收」和统一的元数据表**。题面单独成文件，人读起来方便 |
| [τ-bench / τ²-bench](https://arxiv.org/pdf/2406.12045) | 按业务领域分（航空、零售、电信），由另一个模型扮演用户、多轮对话；判分看最后的数据库状态 | **pass^k**：同一题跑 k 次全对才算稳。我们的锯齿状成绩（v141b-s1224 在干净 112 题上三次 28 / 26 / 21）正适合用这个指标描述。另外有「模拟用户」，专门覆盖用户追问 |
| [BFCL v4](https://gorilla.cs.berkeley.edu/blogs/15_bfcl_v4_web_search.html) | 按类别分组，总分加权：Agentic 40%、多轮 30%、Live 10%、Non-Live 10%、幻觉 / 无关检测 10%；格式敏感性只展示、**不计入总分** | **总分的权重写在明面上**；诊断类题集与计分题集分开。我们的探针本质上就是「不计分的诊断题」 |
| SWE-bench Verified | 从 2294 道原题里由人工筛出 500 道「题意清楚、测试可靠」的子集 | **定期清洗**：把判据有问题、题意模糊的题移出主分，而不是一直累加 |
| HELM | 每个「场景 × 指标」都单独出分，并且明确列出**没覆盖到的场景** | 报告里写「这套题测不到什么」 |
| lm-evaluation-harness | 每个任务一份 YAML，用 group / tag 把任务聚合成套件 | 用一份**注册表**声明「哪些题属于哪个套件」，而不是靠目录名 |
| GAIA | 三级难度，测试集答案不公开 | 留存集要真的「锁起来、定期跑」，否则失去意义（我们的 p13 从没跑过） |

## 6. 整理建议（2026-10-15 已拍板并实施，结果见 §8～§10）

按改动从小到大排列。

### 6.1 先建一份题集总表（不动题目）

新增 `bench/SUITES.md`（或机器可读的 `suites.json`），每套题一行：

| 字段 | 例子 |
|---|---|
| 名字（按用途起） | `work-core-en`（现 workbank）、`probe-bash-2`（现 bash 第二部分） |
| 用途 | 主分 / 辅助读数 / 诊断探针 / 留存 / 下架 |
| 测什么 | 一句话 + 主要能力轴 |
| 工具清单 | work-v1 / work-v2 |
| 语言 | en / zh / 混合 |
| 计分口径 | 例如「干净 112 题，作废计失败」 |
| 已知盲区 | 例如「无中文；用户追问仅 3 题」 |
| 最近一次跑分 | 日期 + 结果路径 |

旧名字继续保留为别名，跑分脚本不用改。

### 6.2 报告改成「能力面板」，不再只报总分

- workbank 按场景出分；另报**有效分**（去掉 RWKV 至今从未做对的题），并单独列出 web、notool 两类。
- 探针单独成栏，不并进总分（参照 BFCL 的格式敏感性）。
- 重要的比较跑 3 次，同时报平均分和「3 次全对」的题数（pass^3）。

### 6.3 统一题目元数据

现在各套题的字段不一致：探针老题没有 `axes`、`family`；workbank 没有语言、用户轮数字段。建议每题都补上下面这些字段，能自动算的由 lint 补：

- `language`：zh / en
- `user_turns`：用户消息条数
- `ref_calls`：参考解的工具步数
- `answer_form`：数字 / 短串 / 关键词 / 文件状态 / 弃权
- `capabilities`：能力轴
- `author`：出题模型
- `contamination`：是否进过训练

### 6.4 补题优先级

1. **中文版 workbank**：先把干净 112 题翻译成平行版，判据不变，可以直接对比中英差距。
2. **用户追问 / 改需求**：现在只有 3 题。可以参考 τ-bench 用模型扮演用户，或者先手写 20 题左右。
3. **长输入、及时停、弃权**：各补到 10 题以上，才能测出变化。
4. script 和 tabular **不删**，但单独标为「能力靶子」。等 RWKV 开始在上面得分，它们就会自然回到有效分里。

### 6.5 流程

- p13 要么定期跑（比如每个推荐点跑一次），要么明确降级为「只用于去重查泄漏」。
- 换出题模型：下一批题避免由老师本身出，或者至少混用两三家，减轻 4.5 的偏向。
- 每季度做一次类似 SWE-bench Verified 的清洗：老师也做不对的题、判据有争议的题，移出主分。

## 7. 口径与局限

- 通过率混合了 88 次不同 state、训练点和采样的 RWKV 跑分，只能看各类题的相对难度，不能当某个模型的成绩。
- 老师只有 2 次跑分。
- 两份第二部分只有 v141b-s1224 的一次跑分（k0）。
- 跑分原始数据在 `local/runs/`，不入库；`analyze.py` 在别的机器上会得到不同的通过率，但构成部分（第 2、3 节）只读 `bench/`，结果一致。
- bfcl-product、boundary、primitive 的题目在 Go 代码和 `internal/agent/eval/` 里，只做了人工统计，没纳入 `analyze.py`。

## 8. 新考卷（已实施）

用户拍板的原则：**考卷题目 = 用户在 App 里会做的事；考卷跑的配置 = App 的默认配置。** 实现如下：

| 部分 | 做了什么 | 位置 |
|---|---|---|
| 总表 + 清单 | 每套考卷一份 JSON 清单（每题一行：路径、内容哈希、任务类型、难点、语言、用户轮数、判分方式），配一份由它生成的 `SUITES.md` | `bench/exam/`，生成命令 `rwkv-lab exam build` |
| 完整考卷 | 380 题 = workbank 干净 112 + p13 60 + bfcl-product 60 + boundary 18 + bash 探针 86 + 天气探针 44；36 道泄漏题不进 | `bench/exam/full.json` |
| 快测版 | 87 题，按「任务类型 × 语言」分层抽，优先有区分度的题，每类留送分和难题各一 | `bench/exam/quick.json`，`rwkv-lab exam select-quick` |
| 内置题导出 | bfcl-product、boundary 从 Go 代码导出成普通题目；去掉「必须用某工具、传某参数」的过程约束，只按结果判分 | `bench/exam/imported/` |
| 自然问法 | 去掉「Reply with only the final answer… UNKNOWN」「reply DONE」，换成 4 种用户口吻的说法（按题目 ID 固定挑选，避免考卷本身变成固定模板）；原题面存在 `tags.legacy_prompt` | `naturalize.py` |
| 判分 | 数字题改为「回答里出现正确数字」（`expected_number_in_text`）；短串改为按词边界包含；应弃权的题改为「点名缺什么 + 说明没有」；取消字数上限 | `internal/agent/eval/scoring.go` |
| 跑分 | `agent-eval --cases bench/exam/<x>.json`，清单自带 `--harness app`：工具和 harness 选项全部由 App 的同一份代码生成，文件改动走暂存、跑完自动确认再判分 | `internal/agent/eval/productharness.go`，`api/eval_harness.go` |

任务类型和难点的定义见 `bench/exam/SUITES.md`「名词」一节。

### 8.1 改写时发现并修掉的判分问题

- **中文答案按词边界匹配一律判错**：旧的按词匹配把汉字当成单词字符，「共33条」里找不到「33」。改为汉字一律视为边界。
- **结尾句暗示只查本地**：最初的两种结尾（「from what's here」「if the data doesn't say」）让模型在 web 题里看了一眼空工作区就放弃。已换成不限定来源的说法。

## 9. App 与评测对齐（已实施）

App 和评测现在共用 `internal/agent/product` 这一份组装逻辑，`api/parity_test.go` 保证两边的系统提示词、工具清单（名字、顺序、schema 哈希）、wire 和兜底参数逐字一致。顺带修掉的 App 问题：

| 问题 | 之前 | 现在 |
|---|---|---|
| 格式 | App 新建连接跑 xml-v1，训练和评测用 g1k | 新建连接默认 g1k（已保存的旧配置不改） |
| 工具 | web、天气、bash 默认关 | 默认全开；没填搜索 key 时工具仍列出，调用时提示去设置里填；缺 bash sidecar 时自动不挂 bash |
| token 预算 | 回答 1024、决策 512（g1k 第一步的思考会被截断） | 4096 / 2048，与跑分规程一致 |
| chat-completions 后端（DeepSeek 等） | 套上 g1k 后 runner 直接报错，会话起不来 | 这类后端不套文本续写的 wire 预设 |
| chat-completions 第一步 | 强制必须调工具（问「六边形几条边」也要先列目录） | 由模型自己决定 |

### 9.1 留给用户决定的一点

App 新建 chat 连接默认**关闭上游思考**（`chatThinking: disabled`）。在 7 道 web 题上，DeepSeek 关思考时只做对 1 道，开思考时 4 道，旧评测配置（开思考）7 道。关思考时它查完本地就放弃，不去上网搜索。要不要把 App 的默认改成开思考，需要你拍板。注意：DeepSeek 开思考时不接受 `tool_choice=required`，而上面已经把第一步改成由模型自己决定，所以现在开思考不会再报 400。
