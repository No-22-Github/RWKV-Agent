# 客户端合批吞吐对照（REPORT）

日期：2026-10-15。方法见同目录 `PLAN.md`，实际执行有三处偏离，下文注明。

## 结论

1. 只有 20ms 窗口的合批（d56f7867）在稳态下**几乎合不到批**：上午几轮跑分的调用到达率只有每秒 0.1–0.6 次，
   20ms 窗口里平均凑不到 0.02 条。除了开跑那一波，其余调用仍是单行请求。
2. 服务端同一张卡上多个请求的解码循环是**轮流执行**的，不共享前向；每卡吞吐只取决于**单个请求里有几行**。
   所以客户端改成"同时在跑的请求不超过 N 个（N≈卡数），其余排队，等有请求结束就合成一个更宽的请求发出"。
3. 新调度（在途 4、单批 64）在单卡 workbank 全量 148 题上：整轮墙钟 580s → 478s（−18%），
   单次调用 p50 38.6s → 20.4s，调用吞吐 59.9 → 75.6 次/分。
4. 整轮只快了 18%，是因为这个负载**以预填充为主**：prompt 与生成 token 之比约 17:1（112 万 vs 6.7 万）。
   合批解决的是解码；剩下的大头是 agent 每一步都要把整段上下文重新预填充，这只能在服务端解决（见"服务端建议"）。

只跑了一次 A/B（没有 A→B→A→B 交替），全量组只跑了 A 和 C。

## 微基准：服务端每步开销

每行固定生成 200 token（`stop_tokens` 设成不会采到的 id），greedy。

| 形态 | 8100 单卡新引擎 tok/s | 8018 网关 3 卡 tok/s |
|---|---|---|
| 1 个请求 × bsz=1 | 117 | 81 |
| 1 × bsz=16 | 1,305 | — |
| 1 × bsz=64 | 4,145 | 2,662 |
| 1 × bsz=128 | 6,315 | 4,438 |
| 8 个请求 × bsz=1 并发 | 163 | 243（分到 3 卡） |
| 48 × bsz=1 并发 | — | 279（分到 3 卡，约等于每卡一个 bsz=1） |
| 4 × bsz=16 并发 | 1,697 | — |
| 2 × bsz=32 并发 | 2,720 | 3,189（分到 2 卡） |

单卡 8 个 bsz=1 并发只比 1 个快 40%：多个请求的解码循环基本轮流执行。8018 网关上的路由器按"在途 bsz"把请求分给最空的卡
（`RWKV_Lightning_CUDA_router` `scheduler.acquire`），所以同时在跑的请求数应约等于卡数。
单卡 bsz=128 时单个请求的上限是 169 行（`bsz overflow, Max bsz=169`，随空闲显存变化）。

预填充（单卡）：1 行 × 4k token 约 2.8k tok/s，16 行 × 4k token 约 5.9k tok/s。

## Agent 对照：全量 148 题

| 组 | 墙钟 | 调用/分 | 单次调用 p50 / p90 | prompt tok/s | 生成 tok/s |
|---|---|---|---|---|---|
| A 不合批 | 580s | 59.9 | 38.6s / 82.8s | 1,843 | 115 |
| C 新默认 | **478s** | **75.6** | 20.4s / 52.8s | 2,361 | 141 |

C 的首 token 等待 p50 从 4.3s 升到 7.1s：一个宽请求要等所有行一起预填充完才出第一个 token。这是用延迟换吞吐，整轮仍然更快。

## 输出一致性

- greedy 下合批与不合批的第一次调用约 80% 文本完全相同。差异来自批维度不同带来的 fp16 数值差，
  B（旧窗口合批）同样是这个比例，与新调度无关；一旦某步不同，这道题后面的步骤自然都会分叉。
- 没有任何一条输出是"不合批输出的严格前缀"，即客户端没有提前截断仍在生成的行。
- 新旧引擎在 `/v1/batch/completions` 上都是整批结束时才一起发各行的 `finish_reason`，跑满 `max_tokens` 的行也报 `stop`。
  客户端据此在同批其他行又走了 64 步、某行仍无输出时判定它已以 EOS 结束（实测服务端每步给每个活跃行各发一个 chunk，行间最大间隔 1 步）。

## 服务端建议（按收益排序，需改 rwkv_lightning_cuda）

1. **批量路径的前缀状态复用**：在每个 prompt 结束处缓存 RWKV state（按 token 前缀哈希），下一步只预填充新增部分。
   本轮 trace 统计：同一道题内能复用上一步 prompt（或 prompt+输出）前缀的部分占 prompt 字符的 77%（g1k）/ 81%（上午 work-v2 MiSS run）；
   各题共用的 system prompt 与工具目录还能再省。合批之后预填充已是大头，这一项预计能让整轮再快一倍以上。
2. **连续批处理**：每卡一个调度循环，每步接纳新行、移除结束的行。RWKV 状态定长，不需要 KV 分页，实现比 Transformer 简单。
   做了之后客户端的在途上限、等待窗口和静默判定都可以删掉。
3. **逐行即时结束信号**：`batch_generate_stream_with_state` 在某行采到停止 token 时立即发这一行的 `finish_reason`
   （现在是整批结束才发），并区分 `length` 与 `stop`。改动约十几行，客户端可以去掉 64 步静默判定。
4. **服务端文本停止串**：批量请求接受 `stop: ["</tool_call>", "\nUser:"]`，命中即结束该行。现在客户端已交付的行
   在服务端仍会一直生成到 EOS 或 `max_tokens`，白白拉长整批。
