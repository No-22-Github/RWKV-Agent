## 0. 先读这里：用到的词

- **原生思考组**：格式 `agent-wire-think-v1.0+recover-preamble`。模型先写 `<think>…</think>`，再写工具调用或最终回答。采样见上文"实验配置"。
- **recover-preamble（兜底）**：思考结束后、`<tool_call>` 前多说了一句话，harness 去掉这句话照常执行。
- **步 / 轮**：“步”＝模型一次生成（一次调工具或一次作答）；“轮”＝用户说话的次数。
- **强制收尾**：同一个工具调用重复，harness 拒绝并要求“只用已有结果作答，不许再调工具”，之后进入“作答阶段”。
- **主因**：脚本按优先级给每个失败运行打一个主标签（先看思考死循环/参数全被拒，再看编造工具、重复调用，再看克制、必调工具未调、文件状态，最后是“答错”）。一题常有多个毛病，所以主因占比只是排序依据。
- 题目标签：scenario 场景（config/logs/tabular/docs/filesystem/web/script/notool/hybrid…），task 大类（find-read 找并读、write 写改、compute 计算、external 外部、answer-direct 直答）。

## 1. 结论（5 行）

1. 开思考后，**格式漂移已不再是主要死因**：修复前两遍里“写法被拒”的约 112 题，修解析器后只多过 5 题左右（见第 11 节），其余死在重复调用、读错数据、改错文件等环节。现在带漂移写法的题通过率（18%–19%）与全卷（30%–31%）相比已无独立解释力。
2. 头号模型问题是**拿到工具结果后“不继承”**：下一步思考几乎照抄上一步的开头，又去调同一个工具，被拒后进入强制收尾，而收尾阶段模型还在吐工具调用（主因占失败的 25%–28%）。
3. 第二是**读到数据却答错**（数数、日期过滤、版本选择、凭空编“今天”，占 27%）；第三是**编造工具名**（11%–12%，含此类的题几乎全灭）。
4. 写类题 125 道里，只有 46/50 题真正写盘成功，写成功的约三成过关；常见问题是 `replace_lines` 区间与内容不匹配，且错了仍说“Done”。
5. 3 轮及以上的 16 题（全是 hybrid 多轮改文件题）两遍全灭，不是越聊越差，而是第 1 轮就有 9–10 题已出错。

## 3. 重复调用与“收尾阶段仍吐调用”（严重度最高）

**现象**：模型读完文件后，下一步的思考几乎照抄上一步（“我需要先读文件”），又调同一个工具，被拒；进入强制收尾后，又继续写工具调用；最后要么胡写，要么说“我没有任务/没有工具结果”。

**规模（脚本）**：
- 被拒的重复调用 159 / 146 步，其中 123 / 108 步重复的是**之前已成功执行**的调用（read_file 62 / 58、list_files 24 / 27、search_text 15 / 10），另 36 / 36 步重复的是之前失败的调用。
- 含重复的题 146 / 135，通过仅 7 / 6；进入强制收尾的题 154 / 140，通过 8 / 7。
- 作答阶段（明确告知不许调工具）仍吐 `<tool_call>` 的步 227 / 192，涉及 86 / 79 题，通过 3 / 4。
- 主因归 DUP 的失败 110 / 96（两遍同主因 60）。

**典型 case**：
- `hyb-14105`（k0）：第 1 步读完 README 后，第 2 步思考与第 1 步几乎一字不差：
  `>The user wants to bump the version from v2.3.0 to v2.4.0 ... I need to read the file first, then use replace_lines ...</think><tool_call>{"name":"read_file","arguments":{"path":"README.md"}}`（被拒）。
  收尾阶段连续 3 步仍写 `read_file`；第 2 个用户轮同样再来一遍。
- `hyb-14129`（k0，“把 logs 目录清空”）：先 `ls` 成功，后面换成 `replace_lines`（参数被拒）→ 重复被拒 → 收尾阶段连写 3 次 `{"name":"bash","arguments":{"command":"rm -f /workspace/logs/*.log"}}`。
- `tab-12003`：同一个读不到的路径调用第二遍被拒，收尾阶段仍写 `read_file`，终答要用户“提供数据”。

**对训练数据的建议**：
- 补“**拿到结果后的下一步**”轨迹：下一步思考必须以“上一步结果里有什么”开头（引用具体内容），然后要么作答，要么换一个**不同**的调用（换路径/换工具），**不能**重复同一调用。示意：
  ```
  <think>read_file 返回了 README：版本是 v2.3.0，安装行是 pip install ledgerline==2.3.0。现在改这两行。</think>
  <tool_call>{"name":"replace_lines","arguments":{"path":"README.md","start_line":3,"end_line":3,"content":"Current release: v2.4.0"}}</tool_call>
  ```
- 补“**作答阶段**”样本：上下文里已有工具结果、系统要求“不许调工具，直接答”时，轨迹必须是**纯文字回答**（不含 `<tool_call>`）。构造方式：取成功轨迹的倒数第二步（已有足够证据），把“要求直接作答”的提示放在最后，目标输出为文字终答。
- 负样本/拒绝样本：同一 (工具, 参数) 在前面已成功时再写同样的调用——标为不可取，对应正确续写是“引用结果并作答”。作答阶段写 `<tool_call>`——标为不可取。
- 作答阶段还要补“复述原问题再答”的样本（训练提示里把原问题放在近处），避免模型说“我找不到原始任务”。

**预估收益**：两遍同主因 60 题；加上主因不同但含重复调用的稳定失败，上限约 60–90 题（约 +5 到 +8 个百分点单遍通过率，实际按一半估）。其中一部分取决于 harness 修收尾提示（见附录），所以数据端能确定救回的约 30–45 题。

## 4. 读到数据却答错（数错、算错、抄漏、选错、编“今天”）

**现象**：证据已读到，但计数差一、日期过滤不到位、选错版本档位、抄进计算器时漏数、遇到“今天”不查日期而是编一个。

**规模**：主因 WRONG 104 / 104（占失败 27%），两遍同主因 70。按题型：number+compute 28 / 24，contains+find-read 16 / 18，contains+external 14 / 16，contains+compute 12 / 14，number+find-read 10 / 6。

**典型 case**：
- `log-13112`（k0）：问“昨天 nginx 重启了几次”，直接 `grep -c "nginx restart"` 得 6（含两天），答“昨天 6 次”；k1 列出 5 行，其中 3 行属于 09-15，答 5。期望 3。随后追问“一周多少次”，模型沿用错数 ×7，答 42/35（期望 21）。
- `hyb-14107`（k0）：问 Beta 发布日期离今天几天，终答“Beta 发布日期是 2026-11-03，今天是 2026-09-25，还有 28 天”（期望 48）。“今天”是从计划文件里的另一个日期冒出来的，没有调日期工具。
- `doc-8011`：用户说“司龄满四年”，文档分档是“满 3 年不满 5 年：10 天”，模型直接答 15（未调任何工具、未读制度）。
- `tab-0007`：均值题，两次读文件路径被拒，之后只列出名单，说“打卡记录不在工作区”。

**对训练数据的建议**：
- **计数/汇总题**：轨迹应是“读全文 → 用 `calculator` 或 `data_query` 的合法聚合做精确计算，而不是靠心算数行”，并且思考里逐行列出被计入的行（带日期/键）。示意：
  ```
  <think>日志里只有 09-14 的行属于“昨天”。符合的行：02:10、20:31、…，共 3 行。用计算器验证。</think>
  <tool_call>{"name":"calculator","arguments":{"expression":"1+1+1"}}</tool_call>
  ```
- **日期题**：凡涉及“今天/昨天/上周”，必须先调时间工具（或用户明示日期），不得从文件里借一个日期当今天。负样本：直接引用文件中的某个日期当“今天”。
- **按条件选档位/版本**：思考里写出“条件→命中档位”的对应，再取值；构造干扰项（旧版、相邻档位）的对照样本。
- **多轮追问**（“你刚才查到的是几次”）：答案必须与上一轮终答一致，且新一轮的推导基于它（该点模型本身做对了，保留即可）。

**预估收益**：两遍同主因 70 题。这类难度较高（模型能力本身），数据端预计能救回其中约 1/3，即 20–25 题。

## 5. 编造不存在的工具名

**现象**：写出 `search_files`、`search`、`create_file`、`send_email` 等不在工具清单里的名字。含此类的题**一题都没通过**。

**规模**：unknown tool 调用 55 / 55 步。最多的是 `search_files`（20 / 18）、`search`（19 / 20），其次 `send_email`、`rename_file`、`remove_file`、`replace_in_file`、`edit_file`、`translator`、`create_file`、`finish`、`message`、`diff`。含此类的题 51 / 47（通过 0 / 0）；主因归此类 46 / 42，两遍同主因 32。

**典型 case**：
- `code-0008`（k0）：先 `search_files`（不存在）→ 改 `list_files` → 读文件后直接 `create_file`（不存在），最后文字说“工具清单里没有 create_file，我只能读、列、搜、追加”。
- `nt-0003`（k0）：要求发邮件，调 `send_email`（不存在）；k1 同题通过（没发明工具）。
- `hyb-14127`：重命名文件时调 `rename_file`（不存在）两次。

**对训练数据的建议**：
- 补“**需求超出工具范围**”轨迹：发邮件、重命名、删除、翻译等，正确做法是只用清单内的工具组合（重命名＝`read_file`+`write_file`，或 `bash mv`；搜内容＝`search_text`），或直接说明做不到。示意：
  ```
  <think>清单里没有发邮件的工具。我可以把邮件草稿写进文件，并告诉用户我无法直接发送。</think>
  <tool_call>{"name":"write_file","arguments":{"path":"drafts/email_ada.md","content":"…"}}</tool_call>
  ```
- 负样本：用 `search_files`/`search`/`create_file`/`edit_file` 等常见别名；构造成“模型写了别名 → 报错 → 正确换成清单内工具”的纠错轨迹，同时保留一批“从不写别名”的干净轨迹（纠错轨迹不要多于干净轨迹）。
- 训练提示里要变化工具清单的顺序和子集，避免模型把别的框架的工具名带进来。

**预估收益**：两遍同主因 32 题，这一类相对容易用数据修，预计救回 15–25 题（还要看后续步骤是否做对）。

## 6. 思考复读停不下来

**现象**：思考不闭合，反复复述同一句话，或编号刷屏，直到被截断。

**规模**：思考未闭合且不含调用的步 130 / 109（涉及 87 / 74 题，通过 4 / 3）；其中 n-gram 重复率超 30% 的“复读”步 86 / 71（67 / 56 题）。主因归此类 35 / 35，两遍同主因 17。其中 102 / 93 步生成不足 1000 token 就被判 length，推测是客户端的复读检测提前截断（未逐步核对配置）；约 25 / 24 步撞满 4096。中文思考更易出现：中文题里中文思考步的未闭合率 11.9% / 11.6%，英文思考步 6.9% / 5.6%，英文题 4.6% / 4.5%。

**典型 case**：
- `hyb-0011`（英文，2048 token）：思考刷成编号列表：`91. Reading the current wholesale charges for Tarnbrook Water in the Meadowford zone (again)`。
- `log-8013`（中文题，作答阶段）：`228. I've tried to read the file again but it was not found.` 一路编号到 4096 token。
- `tab-8013`（中文）：思考里反复写出 ```json {"name":"read_file",…}``` 代码块并解释，始终不写 `</think>`。

**对训练数据的建议**：
- 所有带思考的样本，思考部分控制在短段落（现状中位约 250 字符），**一律以 `</think>` 收尾并紧接工具调用或回答**。思考里不要写编号列表、不要出现代码围栏形式的工具调用（调用只能出现在 `</think>` 之后的 `<tool_call>` 里）。
- 补“**已知信息不足时的短思考**”样本：思考 1–3 句→立刻行动，而不是继续推演。
- 负样本（用于偏好/拒绝训练）：同一句话重复 3 次以上的思考；思考中夹 `<tool_call>` 而无 `</think>`。
- 中文题要有足够多的**中文思考**短样本（同样严格闭合）。

**预估收益**：两遍同主因 17 题，另有 70 多题含此现象但主因另有其归；数据端预计救回 10–15 题。

## 7. 该直答/拒绝/确认时动手；有工具却说没有

**现象**：(a) 提示词里已经给了全部材料，仍去工作区找文件；(b) 破坏性操作（清空目录）不先确认；(c) 缺信息不追问；(d) 反过来，明明有 `web_search` 却说“我没有联网工具”。

**规模**：违反“不该调工具/禁用工具”的题 48 / 54，**通过 0 / 0**（场景分布：notool 37 / 43，hybrid 10 / 10）；必调工具却没调的题 20 / 20。主因归 RESTRAINT 31 / 34（两遍同主因 21），NOTOOL 7 / 7（3）。弃权/不调用类题（abstain+no-call）54 题通过 22 / 23。

**典型 case**：
- `nt-14003`（k0，中文）：提示词里贴着会议记录要总结，模型却 `read_file /workspace/会议记录.txt`（不存在）→ `search_text` → 用英文回答“找不到会议记录，请提供”。
- `hyb-14129`（k0）：“把 logs 目录清空吧”，没有先问“确认删除吗”，直接尝试清空；评分要求出现确认类用语。
- `web-0016`：题面明说“本地没有记录”，模型思考写 `I don't have any tools that can access external information`，终答“我无法联网”，未调 `web_search`。

**对训练数据的建议**：
- **直答样本**：用户提示里带有全部材料（文本、数字、翻译、摘要）→ 思考写“材料已在消息里，无需调用工具”→ 直接作答（在用户语言里作答）。示意：
  ```
  <think>会议记录就在用户消息里，不需要读文件。直接概括成三点。</think>
  德清仓 9 月出库偏慢……（三点，中文）
  ```
- **确认样本**：批量删除/清空/覆盖前，轨迹是“先列出将受影响的内容 → 问一句是否确认”，终答不动手。负样本：直接 `rm`/清空。
- **追问样本**：缺少关键值（新 token 值、哪个月）时先问，不要编值。
- **能力声明样本**：题面要求外部信息且工具清单里有 `web_search`/`web_fetch` 时，必须调用；负样本：“我没有联网能力”。
- 同时保留“确实做不到→明说做不到”的样本，比例要平衡（目前模型两端都出错）。

**预估收益**：两遍同主因 24 题，加上含此现象的 notool 稳定失败，预计救回 15–25 题。这是思考组相对不带思考组的强项（第 2 轮对照里 notool/直答领先 +9 题），继续扩有收益。

## 8. 改文件内容不对；错了仍说“已完成”

**现象**：`replace_lines` 的行区间和内容对不上（只改 1–3 行，内容却给了整个 6 行文件），或把整个文件当补丁；写错了、甚至没写成，终答仍是“Done”。

**规模**：写类题（task=write）125 道，真正有成功写盘动作的 46 / 50 题，其中通过 15 / 15；没有成功写盘的题只过 1 / 2。文件状态不对的失败 96 / 98 题：内容不等于期望 29 / 28、文件根本没生成或不可读 24 / 24、不该存在的文件存在 6 / 6。`replace_lines` 成功执行但内容行数多于所给区间的题 10 / 13（通过 4 / 4）。文件题失败的 94 / 93 道里，终答里有“done/已完成”类措辞的 26 / 23。主因归 EDIT 27 / 33，两遍同主因 18。

**典型 case**：
- `cfg-8004`（k0）：任务“把 retry_limit 改成 5，其余不动”。调用 `{"path":…,"start_line":"1","end_line":"3","content":"<整个 6 行文件>"}`，文件变成 9 行；终答：`Done. … retry_limit was changed from 3 to 5.`
- `hyb-14101`（k0）：改 prod 和 staging 的 timeout，`start_line:"1", end_line:"2"` 却附整个文件内容；终答 `Done. Both prod and staging … now have request_timeout = 60.` 随后第 2 轮又用 `start_line:3,end_line:4` 写入多行内容。
- `hyb-14105`：全程没有成功写盘，收尾阶段文字却说“I've updated the README.md … Changed from v2.3.0 to v2.4.0”。

**对训练数据的建议**：
- **replace_lines 规范样本**：先 `read_file` 看行号 → 只替换**含目标行的最小区间**，`content` 的行数与区间行数一致（或明确说明增删行）。示意（改第 4 行）：
  ```
  <tool_call>{"name":"replace_lines","arguments":{"path":"config/worker-staging.yaml","start_line":4,"end_line":4,"content":"retry_limit: 5"}}</tool_call>
  ```
- **回读核对样本**：写完后再 `read_file`，思考里对比前后，再说“已改”。负样本：写调用被拒或根本没调写工具，却说“已完成”——这类终答必须构造成拒绝样本，正确终答是“没有写成功，原因是……”。
- 一次改多处时，用多个小区间，或 `write_file` 整体重写（并先确认原内容完整保留）。
- 题面要求“其余不动/原资料保留”时，补“只改指定行、其余逐字保留”的样本。

**预估收益**：写类题整体仅 12–13% 通过，是最大的短板之一。两遍同主因 18 题，另有 DUP/FAKETOOL 主因下的写类题；估计救回 15–25 题。

## 9. 路径凭空编造、中文文件名译成英文、找不到就放弃

**现象**：用户没说也没出现过的路径被直接拿去读；中文工作区里把“讲堂/座位导入说明.md”写成 `lecture_hall/seat_import说明.md`；`list_files` 看到真实路径后仍不用；读不到就让用户“提供文件”。

**规模**：ENOENT（路径不存在）报错 166 / 161 次，其中 58 / 59 次的文件名既不在用户消息里，也没在之前任何工具结果里出现；涉及 55 / 54 题，通过仅 4 / 4。

**典型 case**：
- `tab-12003`：`list_files` 已返回 `讲堂/座位导入说明.md`，下一步却读 `/workspace/lecture_hall/seat_import说明.md`（半英半中），重复被拒后终答说读不到预约数据，让用户提供。
- `nt-14003`：读 `/workspace/会议记录.txt`（凭空）。
- `cfg-13401`（中文题）：路径被拒后 `search_text` 两次，终答英文“I couldn't find any config file in the workspace”，未再 `list_files`。

**对训练数据的建议**：
- 轨迹规范：路径**只能来自**用户消息或前序工具结果（逐字复制，保留中文、空格、大小写）；不确定时先 `list_files`/`search_text`，再用结果里的原样路径。示意：
  ```
  <think>list_files 返回了「讲堂/座位导入说明.md」，直接使用这个路径。</think>
  <tool_call>{"name":"read_file","arguments":{"path":"讲堂/座位导入说明.md"}}</tool_call>
  ```
- ENOENT 恢复样本：报错后下一步必须是 `list_files`（目录）或 `search_text`，**不能**换个猜测的路径，也不能立刻放弃。
- 中文文件名/目录的样本比例要明显提高（中文工作区、带空格、带全角符号）；负样本：把中文名译成英文。

**预估收益**：与第 3、4 节有重叠；单独估计救回 10–15 题。

## 10. 工具参数字段乱猜、被拒后原样重试

**现象**：给 `web_search` 加 `num`、`num_results`、`top_n`；`web_fetch` 把 `urls` 写成 `url`；`replace_lines` 写成 `replacement_lines`/`old_text`/`new_content`；`bash` 加 `description`；`read_file` 加 `limit`；`calculator` 里用 `pi`、`sqrt`。被拒后“重试”仍带着被拒或新猜的字段，甚至把数字写成字符串（`"max_results":"10"`）。

**规模**：参数被拒 184 / 177 次，涉及 139 / 137 题（通过 26 / 26）。最多：`web_search` 的 `num` / `num_results`（23+18 / 16+18）、`web_fetch` 的 `url`（18 / 17）、`replace_lines` 区间越界 / 字段不存在（20 / 23）。连续两步收到同一错误的 30 / 17 次。主因归 ARGS（所有调用都被拒，整轮作废）17 / 17。

**典型 case**：`cfg-0005`（k0）：`web_search` 带 `top_n` 被拒，思考写“我只用 query 和 max_results 重试”，下一步带上 `"max_results":"10"`；`hyb-14101` 第一次 `replace_lines` 用 `replacement_lines`（数组）。

**对训练数据的建议**：
- 训练提示里的工具说明要和执行端的参数表**逐字一致**（这是最便宜的修复）；轨迹中的每个调用只含清单字段，数值用 JSON 数字。
- 补“被拒后正确重试”样本：思考引用错误信息里的字段名，下一次调用**删掉**该字段，而不是换一个新猜的。
- 负样本：`web_search` 的 `num*`、`web_fetch` 的 `url`、`replace_lines` 的 `replacement_lines`/`old_text`。

**预估收益**：这部分有 harness 契约过严的因素（附录）；数据端约 5–10 题。

## 11. 格式漂移（开思考后）：现在 harness 能容忍，训练数据仍应只用规范写法

**现象**：(a) `<tool_call>` 内写 OpenAI 外壳 `{"type":"function","function":{"name":…,"arguments":…}}`；(b) 调用 JSON 末尾多一个 `}`；(c) `</think>` 后先说一句话再写调用；(d) 忘写 `</think>`，把 `<tool_call>` 直接写进思考；(e) 一次写多个调用 `<tool_calls>[…]</tool_calls>`。

**规模（按步 / 按题，k0 / k1）**：
- 外壳 92 / 91 步，89 / 89 题（通过 17 / 17）。
- 先说话 93 / 86 步，82 / 80 题（通过 9 / 12）。
- 多一个 `}` 39 / 37 步，31 / 28 题（通过 4 / 5）。
- 调用写进思考、没有 `</think>` 44 / 47 步，44 / 45 题（通过 13 / 14）。
- 一次多个调用 8 / 3 步，7 / 2 题（通过 0 / 0）。
- 合计含 (a)(b)(c) 的题 156 / 155，通过 28 / 30（18% / 19%），全卷通过率 30.0% / 31.4%。仍属于致命的残余格式错误（主因 FMT）11 / 12 题，多为一次多个调用、JSON 转义错误（如 `\$`）和截断。

**核实修复前的说法**：旧两遍（think-k0/k1）里含“被拒写法”的题 84 / 88 题（并集 111 题），那时通过 8 / 7 题；同一批题在 v24 通过 13 / 12 题，净增 5 / 5。其中旧失败转为通过 10 / 9，旧通过转为失败 5 / 4（抖动）。仍失败的 71 / 76 题里，63 / 70 题的死因已不是格式：主因分布（k0）是重复调用/强制收尾 32、答错 14、残余格式 8、复读 3、编造工具 2、参数 2。也就是说，格式修复把“被卡死”的路堵上了，但这批题本来就是多步困难题，后面仍死在第 3、4 节的问题上。**所以不应再把格式漂移当作主要收益来源**；全卷总分 v24 对旧版没有变化（k0 166→166，k1 171→174）。

**典型 case**：`cfg-0011`（外壳）`{"type":"function","function":{"name":"search_text","arguments":{"query":"billing-reconciler","path":"/workspace"}}}`；`hyb-0007`（k0，写进思考且多 `}`）`…"content":"saltmarsh==4.0.2\nverdigris==2.3.5\nclapboard==0.6.2\n"}}}</tool_call>`；`tab-0007`（先说话）`I'll start by reading both the roster and the pick log to gather the data.` 紧接 `<tool_call>…`；`cfg-8012`（k0）`<tool_calls>[{"name":"read_file",…},{"name":"read_file",…}]</tool_calls>`。

**对训练数据的建议**：
- 规范写法唯一：`<think>…</think>` 后**立刻**接 `<tool_call>{"name":…,"arguments":{…}}</tool_call>`；一次一个调用；`name`、`arguments` 是顶层键，**不要** `type`/`function` 外壳；JSON 括号严格配平；`</think>` 与 `<tool_call>` 之间不夹任何话。
- 构造负样本/偏好对：同一内容，规范写法为 chosen，外壳/多 `}`/先说话/一次多调用/调用写进思考为 rejected。
- 需要并行读多个文件时，也拆成**多步单调用**。

**预估收益**：直接收益小（+3 到 +6 题），但能去掉对兜底的依赖，且避免在别的 harness 上重新踩坑。

### 11.1 多出来的 `}` 从哪来：续写探针

**结论**：多一个 `}` 是**普通写法（两个括号收尾）和 OpenAI 外壳写法（三个括号收尾）混在了一起**。模型一旦处在偏外壳的状态，就按外壳的方式多关一层。给定上下文，这几乎是确定的，不是随机噪声。

**在哪里出现**：扫描 7 次跑分（开思考 4 次、不开思考 3 次）约 1.8 万次调用。
- **总体**：多括号率 1.6%。开思考 2.6%，不开思考 1.2%。
- **按最后一个参数**：多行文本 7.9%，单行 0.9%。
- **按工具**：`replace_lines` 15.6%、`write_file` 8.3%、`bash` 7.1%；`read_file`、`list_files` 约为 0。
- **外壳写法本身**：一次都没多写。
- **按题**：集中在少数题，同一题反复出现。

**能稳定复现**：取原始上下文，预填模型自己的输出到 `"}}` 为止，再让模型续写。断点要按模型的真实分词来：`"}}` 在词表里是一个 token，断在引号后会把它拆开，结果失真。
- 原本多括号的 50 步：贪心解码 43 步复现，采样（agent-fast）86% 复现。
- 原本正常的 50 步：0 步多写。
- 多出的括号以 `}</`（词表里现成的合并 token）或 `}` 加换行的形式出现。

**消融**：贪心解码，按组统计还会多写括号的步数。

| 改动 | 原本多括号的 43 步 | 原本正常的 50 步 |
|---|---|---|
| 原样 | 43 | 0 |
| 最后一个参数改成 `x` | 19 | 1 |
| 最后一个参数换成别题的内容 | 17–19 | 3 |
| 清空思考 | 31（共 42 步） | 2 |
| **`<tool_call>` 后加一个换行** | 41 | **22** |

- **参数内容不是来源**：改掉内容能减少一半多，但把会多写的那题的内容搬进正常题，并不会传染。
- **思考只有部分影响**：清空思考只从 43 降到 31。
- **换行是最强的诱因**：正常步骤只要在 `<tool_call>` 后加一个换行，就有 44% 变成 `}}}` + 换行 + `</tool_call>`。这正是模型写 OpenAI 外壳时的排版（`<tool_call>` 换行，`{"type":"function","function":{…}}}`，再换行）。
- **轨迹统计也对得上**：同一题里其他步骤用过外壳写法的，普通写法的多括号率是 4.7%，从没用过外壳的题是 1.7%。

**对训练数据的要求**：
- 调用只用 `<tool_call>{"name":…,"arguments":{…}}</tool_call>`，`<tool_call>` 后面**不换行**。
- 任何样本里都不要出现外壳写法。
- 外壳写法、多一个括号、`<tool_call>` 后换行这三种，可以做成偏好对的 rejected 样本。

harness 一侧：v24 已能接受多出的括号，跑分不再受影响；预填和历史记录也一直保持 `<tool_call>` 后不换行。

探针脚本与原始结果：`local/runs/brace-probe-20261029/`（本机，不入库）。

## 12. 多步之间结论不继承

## 14. 思考语言（中文题用英文想）

**规模（脚本，按步统计思考文本的汉字占比）**：中文题（279 题）的第 1 步思考有 60% / 61% 是中文；之后各步中文思考降到 11%–20%（拿到英文的工具结果后又变回英文）。整个轨迹从未用中文思考的中文题 80 / 76 题。以第 1 步思考语言分组，中文思考的通过率 32% / 31%，英文思考 40% / 41%，差距小。中文思考的未闭合率高（见第 6 节）。中文题终答中汉字占比低于 5% 的 140 / 132 条（多为“只回答数字”的题，不一定有问题）；但输出语言违规确有发生：`nt-14003` 中文题用英文回答。

**预估收益**：语言本身不是直接死因，收益主要体现在降低中文思考复读率；单列 2–5 题。

| `nt-14005`（第一遍）、`nt-13007`（两遍） | 提示词里自带了全部材料，终答的翻译/换算也对（100°C=212°F）。失败只因“不该调工具却调了”（`web_fetch`、`get_weather`）。这是考卷的设计意图，不算错判，只是答案本身没错。 |

**C. 规则把正确答案丢掉**

`nt-0004`：终答含正确的“720 GB per day”，但同一题里先调了编造的 `message` 工具，所有调用被拒，整轮作废、答案被丢掉。这题即使不丢也因“编造工具”失败，所以不是主因，只是同类规则的副作用（见本附录“harness 层待改项”第 3 项）。

另外：作废的 10 题与口径无关，是上下文超 32768 token，多为 `long-input` 或多文件题；要让这 10 题可比，需要换上下文更长的端点，或缩短这些题的提示词。

我逐条核对后**排除**的“看起来像口径问题”的题（模型确实答错）：`wth-0001`/`wth-0003`（模型取错了字段/日期）、`wth-0101`（模型把 `days` 传成 1，工具只返回 3 天，没拿到周六）、`hyb-14107`（模型编造“今天”）、`doc-8011`、`doc-13315`、`fs-8013`、`tab-8002`（只有 9 月数据，模型编出 10 月数据且用英文回答）、`log-14138` / `tab-14139`（数错）、`bfcl_recovery_multi_turn_base_8`（文件内容是 `queue=EMPTY`，模型说“文件是空的”）、`log-0013`（漏抄两条）。

### harness 层待改项

1. **写法过严**：OpenAI 风格外壳和多一个 `}` 合计 239 步被拒（修复前两遍）。**已在 harness v24（`6109780e`）修复**，即本报告正文所用版本。
2. **强制收尾提示没有复述原问题**（见正文第 3 节）。
3. **“所有调用都被拒则整轮作废”会丢掉已经写好的终答**（见正文第 10 节）。受影响的题：`nt-0004`（终答含正确的 720）、`bfcl_irrelevance_2`、`bfcl_irrelevance_21`、`nt-14019`。
4. **参数契约**：`web_search`、`web_fetch`、`replace_lines`、`calculator` 被猜错的字段名占了全部参数错误的大头（见正文第 10 节）。

## 附录 E：方法说明

- 全部数字由脚本对两个 `summary.json` 与 `bench/exam/full.json`（题目语言、用户轮数、答案形式）统计；“出现题数”按题去重，“步”按模型生成计。
- 主因标签是脚本的优先级规则加抽样通读轨迹后得到的近似值，两遍主因相同的稳定失败 236 / 361，其余 125 题两遍主因不同，所以不要把主因占比当精确值。
- 格式漂移按 `model_output` 文本模式统计（外壳、先说话、多 `}`、无 `</think>`），与 harness 自己的修复计数（外壳 88/89、先说话 80/80、JSON 修复 27/24）略有出入。
- “复读”步用 30 字符片段重复率超 30% 判定；“生成不足 1000 token 被判 length”的原因是推断，未逐步核对客户端配置。
- 预估收益是“两遍都失败且主因为该类”的题数上限，再按难度折算，不是承诺；各类互有重叠，不可相加。
