# g1i 工具调用弃权缺陷 —— 模型侧反馈（7.2b + 13.3b）

日期：2026-08-20（Asia/Shanghai）
对象：RWKV 训练侧
模型：`rwkv7-g1i-7.2b-20260805-ctx16384`、`rwkv7-g1i-13.3b-20260805-ctx16384`

## 结论

g1i 系列存在一个可复现的行为缺陷：**只要 prompt 末尾预填了结构化输出的起始锚点（` ```json ` 或 `<tool_call>`），模型就必然补完一次工具调用，无法表达「本轮不该调用工具」。**

我们设计了三种不同语法层的弃权出口，在 240 道 BFCL 负样本上两个尺寸的使用次数**全部为 0**；同一套渲染字节下 Qwen3-8B 能使用其中每一种。

**13.3b 上这个缺陷比 7.2b 更彻底：负样本准确率 0.83%，240 题里 238 条发出了调用。** 7.2b 的 36.67% 看似更好，实际是它的格式坏到 parser 认不出而白拿分（见附带发现一）；13.3b 格式干净，因此 0.83% 是不含格式噪声的纯粹弃权失败率。

唯一的例外是**完全不预填锚点**：此时 13.3b 表现得说得过去（正样本 70.00% / 负样本 83.33%），但 7.2b 会塌到 34.50%。详见 §「不预填时 13.3b 的表现」。

这不是 prompt 工程问题。三种出口的指令都用明确英文写清了触发条件与输出形态，两个尺寸对其中任何一条都没有响应。

## 现象

题集：BFCL v4 `simple_python` 400 题（正样本，应当调用）+ `irrelevance` 240 题（负样本，工具与问题无关，正确行为是不调用）。

| 弃权出口 | 所在语法层 | g1i-7.2b | g1i-13.3b | Qwen3-8B |
|---|---|---:|---:|---:|
| 输出空数组 `[]` | JSON 内部 | **0 / 240** | **0 / 240** | 168 / 240 |
| 输出字面量 `NO_CALL` | 纯文本 | 0（且正样本归零） | 0（同） | — |
| 提前写 ` ``` ` 闭合围栏后作答 | Markdown 结构 | **0 / 240** | **0 / 240** | 139 / 240 |
| 不发 `<tool_call>` 标签（预填开标签） | XML 结构 | **0 / 240** | **0 / 240** | 26 / 240 |
| 不发 `<tool_call>` 标签（不预填） | XML 结构 | 154 / 240 | 199 / 240 | 130 / 240 |

指令原文示例，逐字节进入 prompt：

```
If no listed tool is relevant, return the empty array [] and nothing else.
If no listed tool is relevant, immediately close the code block by writing ``` and then answer the user in plain text.
If no listed tool is relevant, do not emit any <tool_call> block.
```

前四行的条件下，模型 240/240 全部照常输出了一个函数调用。只有在**完全不给锚点**时（第五行）弃权行为才出现。

## 为什么判断是模型层而不是框架层

对照组是决定性的：同一套渲染字节、同一个判分器、同一批题目，只换模型。

正样本 = `simple_python` 400 题，负样本 = `irrelevance` 240 题。

| 变体 | 7.2b 正 | 7.2b 负 | 13.3b 正 | 13.3b 负 | Qwen 正 | Qwen 负 |
|---|---:|---:|---:|---:|---:|---:|
| Markdown 围栏（现状） | 92.00% | 36.67% | **94.00%** | **0.83%** | 87.50% | 26.67% |
| Markdown + `[]` 出口 | 91.00% | 33.75% | 93.75% | 1.67% | 87.50% | **70.42%** |
| Markdown + 提前闭合出口 | 91.75% | 34.17% | 94.00% | 1.25% | 96.00% | **70.83%** |
| Markdown bare（撤锚点） | 0.00% | 100%※ | 0.00% | 100%※ | 87.50% | 55.42% |
| Markdown NO_CALL | 0.00% | 100%※ | 0.00% | 100%※ | 86.75% | 80.00% |
| XML `<tool_call>` 预填 | 91.00% | 1.25% | 93.75% | 0.83% | 95.75% | 12.08% |
| XML `<tool_call>` 不预填 | 34.50% | 64.17% | **70.00%** | **83.33%** | 95.00% | 54.17% |

※ 假分数：模型输出散文，判分器解析不出调用因而判「未调用」给分，非真实弃权能力。

给出弃权出口，Qwen 负样本 +44pp；g1i 两个尺寸动都不动 —— 7.2b 停在 33.75%–36.67%，13.3b 停在 0.83%–1.67%。

还有一个更直接的证据：撤掉锚点的条件下，指令里明写 `Do not output prose or role labels`，模型输出的是 400/400 的散文。**模型遵守的是字节形态，不是自然语言约束。**

## 附带发现一：`arguments` 字符串化是尺寸相关的数据污染，两个尺寸污染在不同协议上

这一条比主问题更容易修，也更可能定位到具体的数据处理环节。

`arguments` 字段被错误序列化成 JSON 字符串（`"arguments": "{\"a\": 1}"` 而非 `"arguments": {"a": 1}`）的比例，**在两个尺寸上正好互补**：

| 协议 | 7.2b 字符串化 | 13.3b 字符串化 |
|---|---:|---:|
| Markdown ` ```json ` 围栏 | **271 / 400** | **0 / 400** |
| XML `<tool_call>` 预填 | **0 / 400** | **162 / 400** |

**7.2b 在 Markdown 下坏、XML 下干净；13.3b 恰好相反。** 同一份数据配方、同一天的 checkpoint（均为 `20260805`），却在不同协议上污染 —— 这更像某一批数据的处理差异，而不是配方本身的问题。

后果是兜底依赖完全不同：

| | 7.2b | 13.3b |
|---|---:|---:|
| Markdown `simple_python` strict | 28.75% | **94.00%** |
| Markdown 兜底（`rwkv-wire-compat-v1`）后 | 91.25% | 94.00%（无变化） |

**我们此前记录的「strict 28.75% → compat 91.25%」这 63 个百分点的兜底增益是 7.2b 特有的。** 13.3b 在 Markdown 下 strict 与 compat 完全同分，兜底解析器一次都没触发。

反过来，13.3b 在 XML 预填下的 162 条字符串化被 strict 正确拒绝，导致该格 strict 只有 56.75%，补上兜底后回到 93.75%。

> **修订说明：** 本报告初版曾写「XML 协议让字符串化归零」。该表述仅对 7.2b 成立，13.3b 上方向相反，已按上表更正。不存在「某个协议天生干净」的结论。

## 不预填时 13.3b 的表现：唯一一个正负样本同时可用的组合

在 14 个「模型 × 变体」格子里，只有一个既保住了正样本、又拿到了真实弃权能力：**13.3b + XML `<tool_call>` 不预填**。

| | 7.2b | 13.3b |
|---|---:|---:|
| 正样本 `simple_python` | 34.50% | **70.00%** |
| 负样本 `irrelevance` | 64.17% | **83.33%** |
| 负样本上主动不发标签 | 154 / 240 | **199 / 240** |

关键是它**在按题目区分**，不是无条件偏向某一侧：

| | 主动发出 `<tool_call>` |
|---|---:|
| 13.3b 正样本（该调用） | **317 / 400** |
| 13.3b 负样本（不该调用） | **41 / 240** |
| 7.2b 正样本 | 155 / 400 |
| 7.2b 负样本 | 86 / 240 |

13.3b 在该调用时开标签的比例是 79%，不该调用时只有 17%，**差距 62 个百分点**；7.2b 分别是 39% 和 36%，**几乎不区分**。

也就是说：**13.3b 在没有任何锚点的条件下，仍然保留了「判断这题该不该调工具」的能力，而 7.2b 基本没有。** 这是两个尺寸之间最实质的能力差异，比正样本准确率的差距更值得注意。

83.33% 的负样本分也**不是**靠解析失败蒙的 —— 199/240 是模型主动选择不发标签，属于真实弃权。

### 但这个组合目前上不了评测矩阵

- 正样本 70.00% 比预填档的 93.75% 低 **23.75pp**，代价太大。
- 同一组合在 7.2b 上完全不成立（34.50%），而我们的评测规格要求两个尺寸、两个档位使用**逐字节相同**的渲染，不允许按模型分支。

因此它现在的价值是**训练侧信号**而非工程选项：它证明「无锚点条件下的弃权判断」这个能力在 g1i 里是可以存在的（13.3b 已经部分具备），缺的是把它和「稳定的结构化输出」同时做到。若 7.2b 能补齐到 13.3b 这个水平，再叠加对预填锚点的弃权能力，就不需要在正负样本之间二选一了。

## 附带发现二：训练数据里混入了 agent 框架运行日志

无引导条件下的模板探测（280 样本，temperature=1.0，无 chat template、无 system、无 stop token，见 `RWKV-Toolcall-Bench` 2026-08-12 报告）中，10.7% 的样本含 emoji，形态高度可疑：

```
</tool_response>
🔄 Iteration 0/100 - Continue your response if you have more to say, or if you
   need to make additional tool calls or sub-agent calls.

Bot: <think>
```

```
</tool_calls>
User: <tool_result>
#### 📋 Consultant Observation: UI5 Web Components Table Sorting Behavior
```

`🔄 Iteration 0/100`、`Bot:` 角色名、`sub-agent calls`，连迭代计数器都在 —— 这是某个 agent harness 的 stdout 日志被当作对话数据收录了。

后果可观测：撤掉锚点后模型输出的正是这套形态，自创了 `🔄 Running in parallel:`、`🔧 Tool selected:`、`❌ No tool can be used to...`。**在缺少明确格式约束时，模型回退到的「默认工具调用形态」是这批脏数据。**

## 同类项目调研：四种绕法，都在推理侧付架构代价

为确认这是否只是我们的实现问题，调研了四个 RWKV Agent 项目。**四个项目全部始终预填 anchor，且没有任何一个让那次带 anchor 的调用自己决定「要不要调工具」。** 这一致性说明我们前述三种弃权形态失败不是形态设计问题，而是方向本身不成立。

| 项目 | 弃权机制 | 决策位置 | 对 BFCL 口径 |
|---|---|---|---|
| RWKV-Scout | 弃权 = 调一个叫 `finish_task` 的控制工具；散文走第二次不同 anchor 的调用 | 生成内 | ❌ 仍输出合法调用 → 判错 |
| 123123213weqw/rwkv-agent | 前置 logit 门控：`search`/`chat` 编为单 token，无 anchor 前向一次，比较两个 logit 的差 | **生成外** | ✅ 不生成调用 → result 空 → 判对 |
| Ai00-X/rwkv-agent-kit | think 块内固定槽位，空值哨兵 `[无]`，靠 state tuning 训入 | 生成内 | ❌ 需重训 |
| RWKV-LH | 结构上不可能弃权：是否用工具由上游确定性 Task Graph 决定，anchored 调用只负责填参数 | 上游 | ❌ 每节点必调用 |

其中 RWKV-Scout 与 RWKV-LH 的 anchor 与我们**逐字节相同**（`Assistant: ```json\n`，围栏故意不闭合），两者都有测试钉死该字面量。RWKV-LH 明确记录了「一次性给全 catalog」vs「先选类型再给单工具 catalog」的消融：工具名正确率 3/5 → 5/5。

四个项目均**没有负样本/irrelevance 测试集**，也没有任何地方讨论「模型不会弃权」。因此本报告的 240 题弃权测量在该生态内是新的。

### 结论：不动模型的前提下，这块没有优雅实现

唯一在 BFCL 口径下也成立的方案是 logit 门控 —— 因为它在判定为「不该调」时根本不发起工具调用那次生成，result 为空，官方判分器解码为 `[]` 即通过。但它有两个硬约束：

- **需要 in-process logits 访问。** 普通续写接口做不到：我们所用推理后端的 `/openapi.json` 中 `logprobs` / `logits` / `logit_bias` / `top_logprobs` 全部缺失，实测传入 `logprobs` 被静默忽略。rwkv-agent 能这么做是因为它直接持有 pipeline 对象、读内存里的张量，不走 HTTP。
- **它替模型做决定，而非修模型的输出。** 这比兜底更进一步，且不可组合 —— 每多一个判断就要多一次前向、一套 few-shot、一个待校准阈值。

我们已验证标签词的单 token 前提成立（`search`=42233、`chat`=24985、`tool`=27176、`是`/`否` 均为 1 token；`CHAT` 会碎成 2 个），但**不采用该方案**：它测到的会是我们外挂分类器的准确率，而不是 g1i 的能力，与本项目「验证 RWKV 能否做 Agent」的前提冲突。

四种绕法各自都在推理侧付出架构代价（额外调用、逐轮切换 anchor、两段式调用、上游确定性图），唯一不付推理侧代价的是 agent-kit 的 state tuning —— 而那正是训练侧的事。**这构成本报告建议第 1 项的主要论据：该能力值得内建，因为生态内所有绕法都不优雅，且都无法在普通续写接口上原生实现。**

## 建议

1. **补「该弃权时弃权」的训练样本。** 关键是包含「结构化前缀已出现，但正确行为是不完成它」这一模式 —— 现有数据里似乎只有「前缀出现 → 补完调用」。BFCL 的 `irrelevance` / `live_irrelevance` 共 1124 题可作形态参考。两个尺寸都需要。
2. **排查 `arguments` 字符串化的来源。** 重点不是「哪个协议更好」，而是为什么同一配方下 7.2b 污染在 Markdown、13.3b 污染在 XML。建议按协议分桶统计训练样本里 `arguments` 的值类型。
3. **清理 agent 日志污染。** 可按 `Iteration \d+/\d+`、`Bot:`、`sub-agent calls`、`🔄`/`🔧`/`📋` 等特征过滤。
4. **把 13.3b 无锚点条件下的弃权判断能力（79% vs 17% 的区分度）作为 7.2b 的对齐目标。** 这个能力在系列内已经存在，不需要从零建立。

## 复现

```
模型   rwkv7-g1i-7.2b-20260805-ctx16384
       rwkv7-g1i-13.3b-20260805-ctx16384
推理   rwkv_lightning（Python 后端，模型列表回显 owned_by=rwkv_lightning）
路径   /v1/chat/completions，contents[] 数组形式 —— 原生续写，不套 chat template
采样   temperature=0.001, top_k=1, top_p=1, 无惩罚
判分   bfcl-eval==2026.3.23 官方 evaluator，未改判分逻辑
数据   BFCL commit 6ea57973c7a6097fd7c5915698c54c17c5b1b6c8
题集   BFCL_v4_simple_python (400) / BFCL_v4_irrelevance (240)
```

两个尺寸的服务端确定性均已单独验证：同一 prompt 连发 4–6 次输出一致，32 题两轮 32/32 逐字节一致；7.2b 有 31/32 与 2026-08-18 的 M2 基线相同。相关的推理侧确定性归因见
[`bfcl-v4-determinism-concurrency-20260820.md`](bfcl-v4-determinism-concurrency-20260820.md)。

> **必须区分两套推理后端。** 上游有两套实现，模型列表的 `owned_by` 字段可以直接区分：
>
> - **`rwkv_lightning`**（Python/FastAPI）—— 本报告使用。`/v1/chat/completions` 接受 `contents[]` 并按原样续写。
> - **`rwkv_lightning_cuda`**（C++/CUDA）—— **不适合评测。** 同名路径改吃 `messages[]` 并套 chat template，默认 `think_type=fast` 会追加 `Assistant: <think></think` 尾巴（模型补上收尾的 `>`，因此每条输出都带 `>` 前缀），且同一 prompt 连发 6 次会出现 2 种结果。该后端的原生续写路径是 `/v1/batch/completions`，`stop_tokens` 也改为整数 token ID。
>
> 接入前先读 `owned_by` 判断后端类型，不要假设同名路径语义相同。

原始输出、逐题判分与六个变体的完整 prompt 均可提供。

## 结论边界（请勿超出此范围引用）

- **只测了 `simple_python` 与 `irrelevance` 两个 split。** 并行调用、多工具选择、长工具表均未验证；XML 的并行调用形态（多个 `<tool_call>` 块 vs 单块内数组）完全未知。
- **Markdown `bare` / `NO_CALL` 两个变体的负样本「100%」是假分数** —— 模型输出散文，判分器解析不出调用因而判「未调用」给分，不是真实弃权能力。凡负样本高分都须先确认模型是否显式使用了弃权形态。§「不预填时 13.3b 的表现」里的 83.33% 已确认为真实弃权（199/240 主动不发标签）。
- **Qwen 的绝对值来自本轮探针的归一化器**，比生产链路低约 9pp（`simple_python` 87.50% vs 生产 96.25%）。全部变体共用同一归一化器，**变体之间可比，绝对数不可外引**。g1i 两列走生产 parser，可与 M2/M2.5 挂接。
- **主表内 g1i 各格的 parser 口径不同**：7.2b Markdown 列为 `rwkv-wire-compat-v1` 兜底分，13.3b Markdown 列与 7.2b XML 列 strict 与 compat 同分，13.3b XML 预填列为兜底分（strict 56.75%）。**不可跨格直接相减**，每格的口径见附带发现一。
- 本报告为格式先验与弃权行为诊断，**不是 g1i 的工具调用能力评分**，不得与 BFCL 公开榜单数值比较。
- 13.3b 的数据为本轮新增（2026-08-20），此前所有 BFCL 记录均为 7.2b；两者不构成同一比较组的历史序列。
- 同类项目调研为**只读源码调研**，未运行任何一方的代码，未复现其报告的分数。四个项目的机制描述基于其源码与文档，其自报成绩（如 rwkv-agent 门控 38/40、RWKV-LH E2E 5/42）按原文记录，未经我们验证。
