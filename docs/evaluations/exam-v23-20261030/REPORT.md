## 与基模对比的口径差异（结论不受影响，但要知道）

基模对照用的是 10-24 格式消融的参照组 `rp`（`local/runs/fmt-20261024/rp-k*`），它和这次有三处不同：

- 后端：当时是旧版 lightning，客户端合批；这次是 1.8.8，服务端连续批处理。
- 工具目录：v2.0 和 v3.2。按 10-21 的结果，基模换目录没有差别。
- harness：v23 和 v25。recover-preamble 两边都开着。

差距有 145 题，远超这些因素可能带来的影响。不过严格来说，这不是"同日、同端点"的配对。用户确认今天不再重跑基模。

## 超时题（基础设施影响，需要知道）

两遍各有 52 / 53 题跑满 30 分钟超时，按失败计。其中 45 题两遍都超时，集中在 script、tabular、hybrid、logs。全卷排队时间（每步拿到首个 token 之前的时间）占模型时间的 83%–84%。基模 `rp` 组当时没有超时题。

这些题即使在另一遍没超时，也只各过了 2 题，所以对总分的影响估计只有几题。但多组判胜时，**各组必须用同样的并发和服务端参数**，否则超时数不同会直接带偏比较。

10-31 的 MiSS 用同样的客户端并发、生成量相近，33 分钟跑完，超时只有 1 / 0 题，排队占比同样约 85%。所以上面的超时不能只归因于预填充，见文末。

## 端点调速记录

上游 1.8.8 的调度方式（`src/inference/rwkv_inference_engine.cpp`）：

- 单线程循环，每轮只做一块预填充（`--chunk-size` 个 token，只属于一个请求），然后让每个解码组走一步。
- 适配器不同就分成不同的解码组。
- 前缀缓存全局 256 条，写死在代码里，按最久未用淘汰，只在每次提示词结尾存快照。

由此定下的跑法：

- `--chunk-size 512`。
- 总并发不超过约 200，保住前缀缓存的命中。
- 不同适配器分开串行跑。

几次失败的尝试：

| 尝试 | 结果 |
|---|---|
| 4×32，客户端合批 | 太慢 |
| 4×64，超过 64 个解码槽位 | EOF |
| 4×16 | 被服务端重启打断 |
| 4×128，总并发 512 | 12:54 服务端断开，原因未查 |
