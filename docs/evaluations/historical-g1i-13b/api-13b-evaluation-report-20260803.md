# RWKV G1I 13B Harness 实测问题报告

日期：2026-08-03  
模型：`rwkv-g1i-13b-4922`  
Harness：当前仓库默认 Agent profile（greedy `top-k=1`、`max_steps=6`、few-shot 关闭）

## 结论

当前 13B 的 route 与工具控制协议稳定，但工具结果后的决策、结构化数据/财务计算、跨文件规划和严格输出格式仍有明显且可复现的问题。

本轮英文 boundary 为 10/18，和 2026-08-01 control run 的分数及 8 个失败 case 集合完全相同。中文定向题在重试一次瞬时 API EOF 后为 2/7；该小样本不是严格的中英文横向对照，但证明同类问题在中文指令下仍然存在。

## 明显问题

### P0：证据充分后不会主动停止

- 18 题中只有 4 题由模型主动完成并停止，14 题依赖 Harness 强制进入回答阶段。
- 51 次工具请求中有 12 次是完全相同的重复调用，占 23.5%。
- 15 次工具错误中，12 次是重复调用被 Controller 拒绝，占 80%。
- 10 个通过任务中有 6 个依赖重复调用拒绝后的强制回答。
- 单文件内容已经完整返回后，常见下一步仍是再次 `read_file` 同一路径。

这说明模型会生成合法工具调用，但没有稳定学会“观察已经足够时立即回答”。

### P0：财务计算不可靠

本轮三个财务 case 全部失败：

1. 多行简单利息：应约为 `289.13`，输出了七行 `0.00`。
2. EUR 支付方案：应比较两个净成本的差额并输出 `EUR by 2686.00`，模型输出 `EUR by 0.5`，把百分比/比例误当成金额差。
3. 外汇列选择：买外币正确用了银行卖出价，但卖外币仍错误使用卖出价；同时违反“只输出数字”，输出整段推导。正确结果是 `28079.50`，模型得到 `27498.5`。

中文利息变体同样失败：正确值 `88.99`，模型输出 `0.00`。

### P0：结构化数据的联合过滤、聚合和对账不稳定

- 英文 JSONL：应为 `orders=6 users=5 revenue=438.72`，输出 `orders=7 users=5 revenue=393.72`。
- 英文订单/退款对账：找对了胜出 SKU，但只输出 `SKU-17`，遗漏必需金额 `1248.50`。
- 中文 JSONL：应为 `订单=4 用户=3 收入=100.00`，输出 `订单=3 用户=3 收入=59.90`。遗漏的恰好是用户 `u2` 的成功订单；同一用户另有失败订单，模型疑似错误地按用户整体排除，而不是逐条联合过滤 `event=checkout && status=success`。

简单 CSV 单列求和与单个 JSON 嵌套字段可以通过，问题主要出现在多条件筛选、跨行聚合和结果字段完整性。

### P1：跨文件规划与失败恢复不完整

- 英文日志题先猜不存在的 `logs` 目录，失败后换了工具但继续使用同一错误路径；回到根目录后只读 `app.log` 和 `deploy.log`，没有读取包含最早部署后 ERROR 的 `worker.log`。
- 中文日志题也先猜 `logs` 目录；随后给 `search_text` 幻觉出不支持的 `after` 参数，最终选中了部署前错误。
- 这类输出的 envelope 与 JSON 都合法，所以协议合法率仍为 100%；问题发生在工具参数语义和执行后的规划层。

### P1：严格输出格式遵循不稳定

- 英文 migration flag 已找到正确参数，但输出整句说明而不是只输出 `--enable-v2-auth`。
- 中文 migration flag 同样输出完整原文，而不是只输出 `--auth-v3`。
- 中文配置值计算正确，但输出英文键名并分三行，没有遵守要求的中文单行模板。
- 外汇题要求只输出数字，模型输出了完整计算过程。

## 中文定向题

首次 7 题中有 1 题遇到远端 `EOF`；单独重试后该题通过。按重试结果替换瞬时服务错误后为 2/7：

- 通过：错误扩展名恢复；中文单文件精确提取。
- 失败：配置输出模板、JSONL 聚合、利息计算、跨文件日志、严格 flag。
- 重试通过的单文件题仍重复读取同一文件，最终由 Harness 强制回答。

这个集合规模较小且难度分布与英文 boundary 不完全一致，因此不能直接断言“中文能力比英文低多少”；可以确定的是，停止、计算、跨文件和格式问题在中文指令下没有消失。

## Harness 与 API 侧需要单独记录的问题

1. `pb_config_precedence_resolve` 答案正确，却因没有调用指定的 `search_text` 被判任务失败。建议报告时同时保留 task success 与 answer accuracy，或允许等价的证据收集路径。
2. API 共观察到一次瞬时 `EOF`，同题重试即通过；不要记为模型能力失败。
3. 服务端所有 usage 字段均为 0，当前无法评价 token 效率或判断具体阶段的预算消耗。

## 当前相对稳定的能力

- `respond` / `inspect` 路由。
- `<tool_call>` envelope 和 JSON 协议。
- 基础单文件读取、简单 CSV 求和、JSON 嵌套字段提取。
- 错误扩展名发现与恢复。
- 基础 prompt injection 忽略。

## 建议优先收集的数据

1. 工具结果后的停止/继续对：证据充分立即回答；缺少明确事实才继续；相同参数调用作为 rejected。
2. 联合过滤与聚合轨迹：逐条应用条件、明确去重维度、列出纳入/排除行、最后做计数和金额校验。
3. 财务映射与校验：买/卖和银行视角、cash/spot 列、百分比与金额差、净流入/流出方向。
4. 跨文件时间排序与恢复：路径不存在后回根目录发现；不幻觉工具参数；收集所有候选文件后再比较。
5. 中英文严格输出契约：只输出 flag、纯数字、固定字段单行，正确值加解释应明确作为 rejected。

如果 Harness 后续提供 calculator 或结构化数据工具，模型数据应重点训练任务拆解、过滤条件、参数生成和校验；精确算术不必全部压在自由文本推理上。
