# RWKV G1I 13B Agent 数据补充反馈

日期：2026-07-30
模型：`rwkv-g1i-13b-4922`
评测：RWKV-Agent `rwkv-agent-eval-v4`，18 个只读文件任务
参考题型：[`marty1885/primitive-bench`](https://github.com/marty1885/primitive-bench)

## 1. 结论摘要

当前 13B 的主要问题不是不会调用工具，也不是工具协议不合法，而是：

1. 获得足够证据后仍继续调用，尤其容易重复完全相同的调用。
2. 工具失败后不会稳定地改变策略，会重复失败调用或继续猜测路径。
3. CSV、JSONL、财务表格等任务中的筛选、列选择、计算和结果校验不稳定。
4. 已找到正确答案时，仍可能不遵守“只输出值”之类的严格格式要求。

Router 和动作协议在本轮均为 100% 合法，因此继续大量补充简单工具 JSON、单文件读取或
基础路由样本，预计收益有限。建议优先补充完整的多步 Agent trajectory，重点训练每次工具
结果之后的“回答、继续、恢复”决策。

## 2. 实测证据

| Runner 策略 | 任务通过 | 工具调用 | 工具错误 | step 耗尽且无回答 |
|---|---:|---:|---:|---:|
| 第一次成功工具后立即回答 | 4/18 | 26 | 9 | - |
| 完全开放连续工具调用 | 10/18 | 65 | 32 | 8 |
| 当前混合状态机 v4 | 10/18 | 54 | 23 | 1 |

当前 v4 的其他指标：

- Route 正确率：18/18。
- 动作协议合法率：71/71。
- 必需工具完成：20/22。
- 必需调用完成：21/23。
- 23 次工具错误中，18 次是重复调用，5 次是猜测了不存在的路径。
- 10 个通过任务中，只有 3 个是模型主动完成并及时停止；另外 7 个依赖 Harness 拒绝重复
  调用并强制进入回答阶段。

8 个失败任务可以归为：

| 类型 | 数量 | 典型表现 |
|---|---:|---|
| 结构化数据与计算 | 5 | 利息、支付差额、汇率列、JSONL 聚合、退款对账错误 |
| 工具规划与错误恢复 | 2 | 猜错目录后重复调用；只读默认配置，没有继续收集覆盖项 |
| 严格输出格式 | 1 | 找到正确 flag，但附加解释导致精确判分失败 |

这说明多工具执行的框架限制已经解除，后续提升点主要位于模型的 Agent 决策和数据推理能力。

## 3. 建议补数优先级

### P0：工具结果后的停止与继续决策

这是当前覆盖面最广、收益最高的一类。

训练目标：

- 工具结果已经包含完整答案时，立即输出最终答案。
- 只有缺少一个可明确描述的事实时，才调用下一个工具。
- 不重复已经成功且参数完全相同的调用。
- 不因为工具仍然可用，就继续无目的地搜索或读取。

建议样本同时包含 0、1、2、3、4 次工具调用，避免模型形成固定的调用次数模式。

正例轨迹应覆盖：

```text
User task
Assistant tool_call A
Tool result A: evidence is sufficient
Assistant final answer
```

```text
User task
Assistant tool_call A
Tool result A: identifies a relevant file but lacks its content
Assistant tool_call B
Tool result B: evidence is sufficient
Assistant final answer
```

偏好或负例应覆盖：

```text
Tool result: evidence is sufficient
Rejected: repeat tool_call A
Preferred: final answer
```

### P1：工具失败后的策略恢复

训练目标：

- `read_file` 文件不存在：先查看父目录或工作区，再选择真实路径。
- `list_files` 目录不存在：退回工作区根目录，而不是重复相同目录。
- 搜索无结果：调整关键词或范围，不能原样重试。
- 连续路径猜测失败后，必须转为发现型工具。

建议构造以下对比数据：

```text
Failed read_file("config.prod")
Rejected: read_file("config.prod") again
Rejected: keep guessing unrelated filenames
Preferred: list_files(".") or search_text("API_TIMEOUT", ".")
```

错误结果必须作为正常 trajectory 的一部分保留，不能只提供所有工具都成功的理想路径。

### P2：结构化数据筛选、计算与校验

当前 8 个失败中有 5 个属于此类。

建议题型：

- CSV 指定列求和、分组、排序和退款抵扣。
- JSONL 按事件类型与成功状态联合过滤，再统计订单、用户和金额。
- 金融表格中的买入/卖出、现钞/即期列选择。
- 多行利息、费用和汇率计算。
- “获胜选项”与“两个选项的差额”区分。

理想回答轨迹应在内部完成：

1. 明确过滤条件。
2. 明确使用的字段或汇率列。
3. 逐项计算。
4. 用计数、数量级或反向计算做一次校验。
5. 按用户要求只输出最终格式。

这里不建议只增加更多心算题。中长期应同时考虑提供确定性的 calculator 或结构化数据工具，
将精确计算交给 Harness；训练数据重点负责正确拆解问题、生成参数和校验结果。

### P3：严格输出格式

训练目标：

- `answer with only the flag`：只输出 flag。
- `answer exactly "SKU amount"`：不得省略金额或附加解释。
- `plain number`：不得添加货币符号、单位、列表或推导过程。
- 用户要求一句话时，不输出多段说明。

建议将“答案正确但附加解释”明确作为负例，而不是语义上判为等价正例。

## 4. 不建议优先补的数据

下列能力在当前测试中已基本稳定，不是近期主要瓶颈：

- `respond` 与 `inspect` 的基础路由。
- `<tool_call>` envelope 和 JSON 字段合法性。
- 单文件读取后提取一个字符串或 JSON 嵌套字段。
- 基础 prompt injection 忽略。
- 简单文件发现后读取。

这些数据仍可作为回归集保留，但不建议占据本轮新增训练数据的主体。

## 5. 数据组成建议

首批 Agent 补充数据可以按以下比例组织：

| 数据类型 | 建议比例 |
|---|---:|
| 工具结果后的停止/继续决策 | 40% |
| 错误路径与工具失败恢复 | 25% |
| 结构化数据筛选与计算 | 25% |
| 严格输出格式 | 10% |

每个任务最好同时提供：

- 一条正确完整 trajectory。
- 一条最有迷惑性的错误 trajectory。
- 明确的 preferred/rejected 对，或可自动判分的最终答案。
- 工具名、参数、结果以及结果是否已经足够回答的标注。

建议增加以下元数据，便于后续切片分析：

```json
{
  "evidence_sufficient_after_step": 2,
  "requires_recovery": false,
  "required_tools": ["search_text", "read_file"],
  "forbidden_repeated_calls": true,
  "output_contract": "exact",
  "reasoning_type": "structured_data"
}
```

## 6. 建议验收方式

补数后的模型应在同一 Harness、同一参数和同一 18 题上复测，并增加未见过的同构题，避免只
记住固定文件名和答案。

建议第一阶段观察：

- Route 和协议合法率保持 100%，不能为了减少调用而回退。
- 重复调用错误由 18 次降到 4 次以内。
- step 耗尽且无回答由 1 次降到 0。
- 工具规划与恢复两题至少通过 1 题。
- 5 个结构化数据/计算失败至少通过 3 题。
- 严格输出题不再因为附加解释或缺少字段失分。
- 总任务通过率从 10/18 提升到至少 13/18，并用未见过的同构题复核。

这些数字是本项目用于验证补数方向的建议目标，不代表模型发布的通用门槛。

## 7. 一句话反馈

> 13B 目前不是不会调用工具，而是工具结果后的停止与恢复策略不稳定。Route 和协议已经
> 100% 合法，但 23 次工具错误中有 18 次重复调用；其次是 CSV、JSONL、财务类过滤计算，
> 以及严格输出格式。建议重点补充“证据充分即回答、缺信息才继续、失败后换策略、禁止重复
> 调用”的完整 Agent trajectory，并加入错误轨迹的偏好对。
