RWKV-Agent · Harness-layer optimization · Control plane only

Without changing the model weights, the Harness raised boundary from 4/18 to 13/18

Model: rwkv7-g1i-13.3b-20260805-ctx16384.
This report covers only the Harness layer, not the inference kernel or UI. Every change below was made with the model weights held constant. What changed was the Runner, protocol, tool contracts, and scoring semantics. It documents how those layers raised an RWKV7 G1i 13B continuation model from 4/18 to 13/18 on read-only agent tasks.

TL;DR · In three points

If you remember only three things

01

Nearly all of the gain came from the Harness, not the model

In one controlled run, only the Harness changed: boundary rose 8→10, answer accuracy 9→12, and tool errors fell 29→16, while model calls stayed at 91. The gain did not come from spending more inference budget.

02

One discipline: no task-specific special cases

Every change was a general Runner rule, tool boundary, or scoring semantic. There was no keyword routing and no per-case patching. That keeps the scores credible and the failure traces useful to the model team.

03

The gap has moved from the control plane to answer accuracy

Against a mature API model, routing, required tools, required calls, and forbidden-tool avoidance all tied at full marks. Of the five remaining failures, only two reflect true reasoning limits; the others still leave room in the Harness or scoring rules.

Why · What raised the score

Three sources, ranked by how honestly they reflect improvement

The important question is not how much the score rose, but why the gain is real. Each source can be independently verified in traces and accounted for separately from model capability.

1

Harness and tool-contract fixes (same model weights)

Many “tool errors” were not the model's fault: malformed paths counted as real observations, nominal absolute paths such as /workspace/… were not normalized, and ill-fitting tools produced wrong answers. Once fixed, the same model replaced fabricated answers with correct facts.

2

Scoring-semantic fixes (recognizing valid paths)

Discovery actions such as list_files / search_text form an equivalence class. If one search_text both finds the file and reads the value, it should not fail for skipping a fixed sequence named by the rubric. This fixes the evaluator, not the model.

3

Bounded convergence catches models that do not know when to stop

The model did not reliably learn to stop once it had enough evidence: 14 of 18 tasks relied on the Harness to force the answer stage. Rejecting duplicate calls, limiting consecutive failures, and reserving a final-answer step means “does not stop” no longer means “returns no answer.”

Playbook · Reusable patterns

17 Harness techniques you can reuse directly

Each card starts with a code anchor (file:line or test name), followed by Problem / Approach / Why / Takeaway. Only portable ideas are included; purely mechanical implementation details are omitted.

A

Make weaker models emit valid control frames reliably

With a continuation backend rather than native function calling, getting the model to open the right frame is difficult. Prefill the most error-prone step deterministically and align the prefix to the tokenizer's actual boundary.

internal/inference/prompt.go:73Protocol

Half-tag prefill: stop at <think and leave the final > to the model

Problem
Completing the prompt with the visually complete <think> actually breaks continuation quality.
Approach
Deliberately end the prefix at <think without >, let the model generate >, and restore the prefix with reconstructOutput before parsing.
Why
The RWKV tokenizer merges > with following text, so …<think and …<think> have different trailing token sequences. Adding > makes continuation begin at a token boundary absent from the training distribution.
Takeaway
Prefill must stop at a token boundary that really appeared during training, not at a string that merely looks complete. TestFastThinkingRendererUsesExactTokenBoundary locks in this contract.
internal/agent/protocol.go · ToolPrefixProtocol

Prefill the first tool action with <tool_call>; the model only completes the JSON tail

Problem
Asking the model to decide whether to open a frame, which frame to use, and what arguments to fill compounds errors.
Approach
On the first inspect action, prefill <tool_call> as the assistant prefix. The model emits only the constrained JSON tail; the Runner reconstructs the full frame and performs strict envelope and JSON parsing.
Why
Opening the frame, a frequent failure point, becomes deterministic framework behavior. The model's freedom is narrowed to the content it should actually own.
Takeaway
Where format correctness and content correctness are coupled, use prefill to separate the format half and give it to the framework.
internal/agent/runner.go · plain-text first turnProtocol

Hybrid gating: only output beginning with <tool_call> enters strict frame parsing

Problem
Forcing every output through a strict JSON envelope turns simple, directly answerable turns into protocol errors.
Approach
Allow ordinary text as a direct answer on the first turn. Only output beginning with <tool_call> enters strict control-frame parsing. Text finals and G1I tool-control frames share one output semantic and submission boundary.
Takeaway
Trigger protocol strictness on demand, not for the entire run. A low-friction path for tasks that need no tools improves both compliance and user experience.
B

Do not let the model pretend it finished

Deterministic host rules guarantee answer integrity; a prompt asking the model to behave does not. The key is to distinguish “obtained a trustworthy observation” from “did not” at the transaction layer.

internal/agent/runner.go:606, 981Evidence

No evidence, no submission: ErrNoWorkspaceEvidence + transaction rollback

Problem
Every tool fails, yet the model invents and submits an answer anyway—for example, hallucinating --migration-flag=2.4.0.
Approach
If an inspect turn attempted tools but obtained no trustworthy observation, fail with ErrNoWorkspaceEvidence and roll back the entire turn. Do not generate or submit an evidence-free answer.
Takeaway
“A trustworthy observation is a prerequisite for an answer” must be a hard constraint, not a request in the prompt.
internal/agent/runner.go:695Evidence

Classify evidence reliability: argument errors are not real observations

Problem
A malformed-path error (bare fmt.Errorf) was treated as having reached the workspace, setting hasToolEvidence and defeating rollback.
Approach
toolEvidence := !errors.Is(err, ErrInvalidToolArguments): an argument error rejected before the tool touches the world is not an observation. A missing file (lstat) or runtime failure did touch the world and remains trustworthy evidence. An out-of-bounds rejection is itself a reportable observation.
Takeaway
Classify every tool error explicitly. “Rejected by argument validation before touching the world” and “failed after touching the world” are different; only the latter can ground an answer.
internal/agent/protocol.go · final-answer leak checkSubmission

Block protocol leaks before submission; abstain deterministically but preserve raw output for scoring

Problem
The model emits protocol tags, role headers, whole JSON objects, or raw tool payloads directly to the user as its answer.
Approach
Reject these leaks before submission. Write a deterministic abstention to the user transcript, but retain the raw model output separately for answer_accuracy and report answer-contract repair rate on its own.
Takeaway
Account for safety fallback and capability separately. Do not let a safety repair silently hide the model's real weakness, or the fallback will look like model improvement.
C

Bound convergence and treat failure as a normal path

Agent loops commonly fail in three ways: unbounded retries, an increasingly polluted context, or an empty answer at the step limit. The following patterns give each failure a deterministic exit.

internal/agent/runner.go · dedupe/rate limit/reserveConvergence

Reject duplicate calls + limit consecutive failures + reserve a final-answer step

Approach
Reject exact duplicate calls without executing them, whether the original succeeded or failed. Execute no more than two consecutive failures for the same tool and block the third. After any tool attempt, reserve one final-answer step.
Why
If the model cannot learn to stop when it has enough, make sure continued attempts cannot end in an empty answer at the step limit. With insufficient evidence, converge to an explicit limitation instead of a blank response.
Takeaway
A deterministic exit for a model that will not stop is far more useful than increasing MaxSteps.
ErrUnclosedThink / ErrOutputTokenLimitConvergence

Corrections must match the failure: runaway reasoning → immediate </think>

Problem
An unclosed <think> and exhausted output budget were both lumped into “missing envelope,” so the correction prompt addressed the wrong problem.
Approach
Split them into distinct sentinels, with ErrRouteTokenLimit on the route side, and dispatch corrections by error type. Runaway reasoning is told to emit </think> immediately and not reopen reasoning.
Takeaway
A generic “format error, try again” does not fix runaway reasoning. Classify the cause first, then target that class with the correction.
internal/agent/runner.go · retryEchoConvergence

Protocol retries do not write runaway output back into context

Problem
A retry wrote the previous runaway reasoning into the transcript, so the second attempt failed the same way in an even dirtier context.
Approach
Discard runaway raw output during retries with retryEcho, fixing both the decision and route retry paths.
Takeaway
A retry should begin with a cleaner context than the last attempt. Otherwise it merely steps into the same hole again.
internal/agent/tools.go · /workspace normalizationRecovery

Normalize nominal absolute paths: show the right shape instead of allowing five guesses

Problem
The model cannot see the real temporary root, so /workspace/x is a reasonable guess. The old error gave no valid shape, leading to five retries until the budget ran out.
Approach
Map nominal absolute paths to candidate relative paths and accept only candidates that actually exist inside the workspace after normalization. Put the corrected path shape directly in the error. Real escapes such as /etc/hosts still fail.
Takeaway
A tool error's first job is to help the next call succeed. Giving the valid shape in the error is more useful than rejection alone.
D

Make experiments attributable

Under greedy decoding, the prompt is the only input that can explain a changed output. Without recording prompts and reconstructing finish reasons, any score movement becomes guesswork.

rwkvlightning/client.go:470 · inferFinishReasonMeasurement

Infer finish_reason locally or the entire protocol-compliance metric is wrong

Problem
The server does not return finish_reason. A max_tokens truncation was misreported as a protocol-format error; with server-side stop enabled, the stop sequence disappeared and FinishUnknown marked a correct <route>inspect as an unclosed envelope. In testing this drove route to 0/18.
Approach
Infer it client-side: if generated tokens reach the budget, record FinishLength; if output exists below the budget, record FinishStop.
Takeaway
For a non-streaming backend with no usage data, reconstruct finish reason from token counts or “protocol compliance” becomes a false metric.
Step.Request · TracePromptBytesMeasurement

Trace at prompt granularity: full prompt + byte count + tool list

Problem
Old traces recorded only model_output. Under greedy decoding, changing the tool list moved the score, but no one could attribute it to a specific prompt change.
Approach
Record the full prompt, byte count, assistant prefill, stop, max_output_tokens, and the decision stage's tool list for every generation. Also record every route attempt's prompt, output, and parse error.
Takeaway
A greedy evaluation without prompt records cannot be attributed. Identical item-level reruns with the same parameters prove that recording itself does not alter behavior.
controlled single-task A/B · pb_missing_file_recoverMeasurement

Prompt traces prove score drift came from the tool-list change, not capability regression

Evidence
The tool registry was the only difference: the decision prompt changed from 2622 → 2263 bytes, with the first divergence at byte 1505—exactly the 359-byte description of structured_query. The first action changed from search_text{case_sensitive:true} to {case_sensitive:false}. Both answers were correct, but the latter no longer passed through the rubric's required list_files.
Takeaway
The tool list is rendered into every decision prompt under Available tools:. Removing one tool can therefore shift every case's trajectory even if that case never calls it. Any tool-list experiment must record both the list and prompt byte count.
E

Simplify: remove one tool, then one entire stage

Both removals were tested on the RWKV7 G1i 13B model. Prompt traces came first, so we could verify that the score truly did not regress after deletion.

remove structured_query · v8→v9Simplify

An ill-fitting tool is worse than no tool

Problem
structured_query could not express multiple metrics, column selection, or joins. With it, the model returned 355.72 instead of 438.72 and $1,499.50 instead of 1248.50.
Approach
Remove it from boundary and narrow ComputeTools to calculator only. Complete the task through a read_file + calculator composition instead.
Why
After removal, both tasks were answered correctly using only read_file, without even calling calculator. The model's own arithmetic was already correct; the ill-fitting tool was actively producing wrong answers.
Takeaway
Before registering a tool, ask whether it can fully express the task. A partially expressive tool pulls the model toward answers that are executable but semantically wrong.
--route-stage off by default · v11Simplify

Remove the entire route stage: cheaper, steadier, no score regression

Problem
Route was early scaffolding for smaller models and cost one extra model call per turn.
Approach
Disable it by default for the RWKV7 G1i 13B model: boundary stayed at 13/18, model calls fell 69→48, latency 345s→250s, protocol compliance rose 96.1%→100%, and assistant improved 2/6→3/6.
Why
In the one improved assistant case, the model's behavior was already correct—a proper clarification with zero tool calls—but the route assertion marked it as a failure. That stage had become the case's only source of failure.
Takeaway
Scaffolding should have a one-switch off state and default off for capable models. Scoring must follow: if a skipped stage were still scored, it would receive a free 100%. Gate it with the manifest's route_stage field.
F

Recognize valid paths and report two scoring views

The evaluator can create false negatives of its own. Treat it as a variable and account for it separately from model capability.

eval/runner.go:558 · discoveryToolsScoring

Discovery-tool equivalence: one search can complete two steps without failing

Problem
In v9, several fully correct answers lost points solely because they did not follow the rubric's fixed list→read sequence.
Approach
Treat list_files / search_text as an equivalence class. Any discovery tool can satisfy discovery requirements in required_tools, and required_calls may reuse an already matched step. Non-discovery tools such as calculator still match strictly by name.
Takeaway
A rubric should reward achieving the objective, not reproducing the path its author imagined. A fixed sequence penalizes more efficient solutions. TestBoundaryScoringAcceptsEquivalentDiscoveryPaths and ...StillRequiresInvestigation jointly guard the boundary.
Result
RWKV rose 10/18 → 13/18 and DeepSeek 13/18 → 17/18, with no new failures on either side.
answer_accuracy vs task_successScoring

Report both strict and semantic scores, not just one

Problem
The facts were correct, but an added explanation or a Chinese-formatted date caused strict string scoring to mark the answer wrong.
Approach
Report both a strict score, such as 10/18, and a semantic score, such as ~14/18, with answer-contract repair rate separate. Accept either ISO or Chinese date formats and equivalent fallback wording such as “unavailable.”
Takeaway
“Did not follow the format” and “got the facts wrong” are different failures. Combining them into one number distorts model-training priorities.

Principles · Transferable lessons

Six principles that hold across projects

01

Enforce integrity in the Controller; do not request it in a prompt. “No answer without a trustworthy observation” should be a hard constraint with transaction rollback.

02

Measure accurately before optimizing. Under greedy decoding, trace at prompt granularity and infer finish_reason, or both protocol compliance and attribution are false.

03

Classify tool errors. Rejection before touching the world and failure after touching it are different; only the latter is evidence.

04

An ill-fitting tool is worse than no tool. It pulls the model toward an executable but semantically wrong answer. Confirm that a tool can fully express the task before registering it.

05

Design a deterministic exit for models that will not stop. Duplicate rejection, failure limiting, and a reserved answer step are more useful than raising MaxSteps.

06

The evaluator is a variable; keep two ledgers. Reward achieving the goal, not reproducing a path. Report strict and semantic scores separately instead of hiding responsibility in one total.
