## E1（none state）：主桶治好，通过率反跌

人工核实的两大主桶**近零**：信息源选错（纯本地调 web 6→0/28；cfg-0002/code-0001/doc-0002/tab-0001/tab-0002 等全部从 web_search 改为 search_text/read_file）和 step-1 结构断裂（4→**0**，信封/think 全闭合；UNKNOWN 终态 6→0）。**这两个缺陷是语料可治的。**

但通过率 3→0，死因换成三样：
1. **nt 四题全因过度调用判负**（nt-0002 连调 3 次 web_search，答案内容 "HTTPS 443" 本身是对的；nt-0001 calculator 算式数值正确）——S0 仅有的 3 个通过题全灭，overcall 形态与 DeepSeek 镜像；
2. **~8 题内容正确、整句散文不合 plain-number 契约**（cfg-0002、code-0003、doc-0003 等）——closeout 报告 §7.2 的答案契约议题被这枚 state 放大成主要死因；
3. **重复调用翻倍**（前 3 步 9→19、全程 B4 首发散 12 题）：更敢调 → 更容易撞 duplicate → 强制收尾 → 复读链仍在（answer 调用 28→33）。

## E2（fast_think + think-fast）：复读病消灭，变成直答模式

- **answer 阶段复读从 28 次降到 4 次**（closeout 遗留的最强治疗）；
- 编造/绝对路径 0/40；
- 但 **22/40 全程零工具调用**：模型在空 think 后直接作答——工具参与度崩塌。直答质量差：nt-0001 口算 2.5 MiB/s×3600s 得 "90 MiB per hour"（正解 9000，跳过了目录里的 calculator）；doc-0003/web-0002 工作区里有数据却答 "I cannot determine the answer."（under-calling 版的信息源病）；
- 32 个有答案的失败题：14 prose-not-number、13 内容错、其余杂项。

## 判定与下一轮

两枚 state 都是**真实且大幅的能力重排，但都不是净提升**；最有价值的发现是方向性：

1. **信息源选择与结构闭合可由语料训练修**（E1 证明），不是模型不可救的硬伤；
2. **收尾复读可由训练修**（E2 证明），且不需要动 answer 阶段 wire；
3. 两者的失败模式互补：E1 敢调不会收、E2 会收不敢调。**组合方向**：none 语料 + 收尾/判停判例（治 E1 的重复与复读）+ no-tool 判例（治 overcall）；或 fast_think 语料补工具参与判例（治 E2 的直答倾向）；
4. **答案契约（plain number）已成第一死因**（E1 ~8 题、E2 14 题内容正确或接近正确卡格式）——题库层决议（closeout §7.2）的优先级应提高：允许单位/叙述格式或判分侧抽取数字。

## 前缀命中验证（字节级，hex 为准）

fast_think 语料的 assistant 轮一律以「空 think 块」前缀开头（think 开标签 + 立即闭合，hex `3c7468696e6b3e3c2f7468696e6b3e`；corpus.py 在 `prefill=='think-fast'` 时把该前缀拼在 assistant 开头，loss span 从前缀之后起算）。think-fast 变体 300 行采样含 902 个该前缀，none 变体 0 个。

E2 的 wire（`+think-fast`）每次生成前 prefill 同一前缀但**扣掉最后一个 `>`**（hex `3c7468696e6b3e3c2f7468696e6b`，withheld `3e`）——模型第一个 token 补 `>` 即落在训练分布上，与 E2 全部 step 输出以 `>` 开头一致。E1（none）：训练行 assistant 无任何 think 标签，wire 是裸 `Assistant:`。工具信封两侧同套（`ILD{...}WAVE` 信封的 hex `3c746f6f6c5f63616c6c3e` 在两变体训练词表中均存在，与 wire 示例及 E1 实际输出一致）。

**结论：两组 run 都真实命中各自 state 的训练分布；E1 的 overcall 与 E2 的直答倾向是 state 本身的行为，不是前缀未命中的伪影。**
